# 故事单元模式设计文档

> 版本：v1.0
> 日期：2026-07-06
> 状态：设计完成，开始实施

---

## 一、设计背景

### 1.1 问题提出

传统逐章写作模式存在以下痛点：

1. **情绪闭环被打断**：情绪刚推上去，字数到了，被迫断章，下一章重新铺垫导致情绪泄掉
2. **人物被章节节奏绑架**：每章 2500-3000 字的限制，容易陷入"这段对话够不够撑一章"的计算
3. **伏笔布设不从容**：写到第 6 章才想起来第 3 章应该埋个线索的尴尬
4. **跳写困难**：必须按时间线顺序写，想先写高潮部分成本极高
5. **调整成本高**：想调整剧情顺序，牵一发而动全身

### 1.2 核心理念

**故事单元优先，章节后置。**

先以"故事单元"为单位创作（每个单元有独立起承转合），全部写完后再拆分组合成章节。

---

## 二、核心概念

### 2.1 什么是故事单元

一个有独立起承转合的剧情块，比如：
- 一次对峙
- 一场冒险
- 一次揭秘
- 一段关系变化
- 一个转折

每个单元 3000-15000 字不等，该多长就多长，不受章节字数限制。

### 2.2 二维时间线

单元模式引入二维时间概念：

| 时间线 | 说明 | 排序依据 |
|--------|------|---------|
| **创作时间线** | 作者实际写作的顺序（可跳写） | created_at |
| **故事时间线** | 读者看到的故事内顺序 | story_order |
| **章节时间线** | 章节化拆分后的顺序（现有系统） | chapter_no |

### 2.3 单元与章节的关系

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  故事单元创作  │ →   │  单元拆章    │ →   │  章节精修发布 │
│  (上游创作)   │     │  (桥梁工序)  │     │  (下游流程)  │
└─────────────┘     └─────────────┘     └─────────────┘
       ↑                    ↑                    ↑
  新增单元管理模块       新增拆章功能        现有系统完全不变
```

**关键原则**：单元是上游，章节是下游。拆章完成后，所有现有章节流程（编辑、潜文本、一致性检查、TTS、导出）完全不变。

## 三、架构设计

### 3.1 整体架构

```
┌──────────────────────────────────────────────────────────┐
│                    故事单元层（新增）                       │
│  ┌──────────────┐  ┌──────────────┐  ┌───────────────┐  │
│  │ story_unit   │  │ unit_splitter│  │ story_unit_tab│  │
│  │ _service.py  │  │     .py      │  │     .py       │  │
│  └──────┬───────┘  └──────┬───────┘  └───────────────┘  │
│         │                  │                             │
│         ▼                  ▼                             │
│  ┌───────────────────────────────────────────────────┐   │
│  │           记忆系统 + 角色追踪 + 压力 + ...          │   │
│  │         （扩展单元版接口，老接口保留）               │   │
│  └──────────────────────┬────────────────────────────┘   │
└─────────────────────────┼────────────────────────────────┘
                          │
                          ▼
┌──────────────────────────────────────────────────────────┐
│                  章节层（现有，完全不变）                   │
│  章节CRUD / 编辑器 / 潜文本 / 一致性 / TTS / 导出 / ...    │
└──────────────────────────────────────────────────────────┘
```

### 3.2 设计原则

1. **不破坏现有功能**：所有现有接口 100% 保留，新增单元版接口
2. **渐进式迁移**：用户可以选择用单元模式，也可以继续用传统章节模式
3. **数据双写**：单元数据和章节数据并存，拆章完成后回填 chapter_id
4. **单元级隔离**：每个单元有独立的入口/出口状态，错误不扩散

### 5.1 新增服务：story_unit_service.py

**核心功能**：
- 单元 CRUD（增删改查）
- 单元排序（调整 story_order）
- 单元入口/出口状态管理
- 单元专属记忆管理
- 单元状态流转（draft → writing → completed → split）

**主要接口**：
```python

get_unit(unit_id) -> Unit

update_unit(unit_id, **fields) -> Unit
delete_unit(unit_id) -> bool
reorder_units(project_id, ordered_ids: list[str]) -> bool
set_entry_state(unit_id, characters, world, commitments) -> Unit
```

### 5.8 新增服务：unit_splitter.py

单元拆章器——把一个单元拆成多个章节。

**核心功能**：
- 自动检测潜在断章点（天然钩子、情绪高点、场景转换）
- 交互式确认断章点
- 一键拆章，生成章节数据
- 自动回填 chapter_id
- 自动迁移记忆/角色/压力等数据到章节

**主要接口**：
```python
analyze_split_points(unit_id) -> list[SplitPoint]  # 分析断章点
split_unit(unit_id, split_points: list[SplitPoint]) -> list[Chapter]  # 执行拆章
```

## 七、工作流设计

### 7.1 完整工作流

```
1. 规划阶段
   ├─ 创建项目
   ├─ 设计故事单元列表（全局视角）
   ├─ 排列单元顺序（story_order）
   └─ 为每个单元设计入口状态

2. 创作阶段（可跳写）
   ├─ 选中一个单元
   ├─ 配置单元上下文（专属记忆、潜文本卡）
   ├─ 开始写作（AI 辅助 / 手动）
   ├─ 写完后自动同步世界观/角色
   └─ 记录出口状态

3. 章节化阶段
   ├─ 选中已完成的单元
   ├─ 分析断章点
   ├─ 确认/调整断章点
   ├─ 一键拆章
   └─ 自动迁移数据到章节

4. 精修阶段（走现有章节流程）
   ├─ 章节编辑
   ├─ 潜文本卡（章节级）
   ├─ 一致性检查
   ├─ TTS
   └─ 导出
```

### 7.2 跳写支持

跳写的关键是**入口状态必须明确**：

1. 创建单元时，手动定义入口状态
2. 或者从前一个单元自动继承出口状态
3. 写的时候，上下文从入口状态开始组装
4. 写完后，自动生成出口状态

## 九、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 数据模型复杂度上升 | 中 | 双写并存，老接口不变，渐进式迁移 |
| 用户学习成本上升 | 中 | 默认隐藏单元模式，高级用户可开启 |
| 拆章质量不如预期 | 高 | 先半自动（推荐断章点，人工确认），再优化 |
| 单元排序调整后状态不一致 | 中 | 调整顺序后自动触发连贯性检查 |
| 跳写导致前后矛盾 | 中 | 严格的入口/出口状态校验，写后一致性扫描 |

## 十、总结

### 10.1 核心价值

1. **创作自由度**：可跳写、可并行、可调整顺序
2. **质量提升**：情绪闭环完整，伏笔布设从容
3. **上下文可控**：从被动切片到主动配置
4. **错误隔离**：单元级边界，污染不扩散

### 10.2 改动量评估

| 模块 | 改动类型 | 工作量占比 |
|------|---------|-----------|
| 数据库 | 新增表 + 加字段 | 10% |
| 记忆系统 | 扩展接口 | 15% |
| 角色/压力/世界同步 | 扩展接口 | 15% |
| 潜文本/一致性 | 扩展接口 | 10% |
| 单元管理服务 | 新增 | 15% |
| 单元拆章器 | 新增 | 15% |
| UI 界面 | 新增 | 20% |
| **总计** | | **100%** |

**现有系统改动量 < 25%（主要是加接口），75% 是纯新增代码。**
