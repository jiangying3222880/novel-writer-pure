## 一、设计背景

### 1.1 现有架构的问题

现有大纲层级：
```
项目 → 分卷(books) → 章节(chapters) → 章节大纲(chapter_briefs)
```

**问题**：
1. **章节是发布单位，不是创作单位**：用章节来做大纲，本质上是用"发布粒度"来做"创作粒度"，不匹配
2. **编排师被束缚在章节里**：orchestrator 只能 `run_chapter()`，每章 2500-3000 字，情绪闭环容易被打断
3. **大纲没有因果结构**：章节之间是线性排列的，看不到"因为A所以B"的关系
4. **拆章/合章成本高**：想调整章节数量要改很多地方

### 1.2 核心洞察

> **章节是发布层面的概念，单元才是创作层面的概念。**
>
> 大纲应该在"单元"层面编排，章节是最后拆出来的产物。

## 二、新架构总览

### 2.1 三层架构

```
┌─────────────────────────────────────────────────────┐
│                    创作层（上游）                      │
│  分卷(Book) → 故事单元(Unit) → 单元大纲(UnitBrief)    │
│                      ↑                               │
│               编排师负责这一层                         │
│         （因果编排 + 单元写作 + 质量把控）             │
└──────────────────────────┬──────────────────────────┘
                           │ 拆章 (unit_splitter)
                           ▼
┌─────────────────────────────────────────────────────┐
│                    发布层（下游）                      │
│        分卷(Book) → 章节(Chapter)                    │
│                      ↑                               │
│           现有系统完全不变，继续工作                    │
│    （编辑 / 潜文本 / 一致性 / TTS / 导出）            │
└─────────────────────────────────────────────────────┘
```

### 2.2 核心变化

| 维度 | 旧架构 | 新架构 |
|------|--------|--------|
| 大纲基本单位 | 章节 | 故事单元 |
| 编排师工作对象 | 章节 | 故事单元 |
| 章节的定位 | 一等公民（创作+发布） | 拆章产物（仅发布） |
| 大纲结构 | 线性列表 | 因果网络（单元 + 因果边） |
| 调整粒度 | 章级调整（拆/合麻烦） | 单元级调整（灵活） |

## 三、数据模型设计

### 3.1 story_units 表调整

**现有问题**：story_units 直接挂在 project 上，没有 book_id。

**调整**：加 `book_id` 字段，单元属于分卷。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | TEXT PRIMARY KEY | 单元 ID |
| project_id | TEXT NOT NULL | 项目 ID |
| book_id | TEXT | **分卷 ID（新增）** |
| unit_no | INTEGER | **卷内单元序号（新增）** |
| title | TEXT | 单元标题 |
| unit_type | TEXT | 单元类型 |
| story_order | INTEGER | 全局故事顺序（保留） |
| status | TEXT | 状态 |
| ... | ... | 其他字段不变 |

### 3.2 新增表：unit_briefs（单元大纲）

对应旧架构的 `chapter_briefs`，但是单元级的。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | TEXT PRIMARY KEY | ID |
| unit_id | TEXT NOT NULL | 单元 ID |
| brief | TEXT | 单元大纲（整体描述） |
| core_events | TEXT | 核心事件（JSON 数组） |
| emotion_arc | TEXT | 情绪弧线 |
| cause_summary | TEXT | 前因总结（承接上一单元的什么） |
| effect_summary | TEXT | 后果总结（引出下一单元的什么） |
| hooks_planted | TEXT | 本单元埋设的伏笔（JSON 数组） |
| hooks_paid | TEXT | 本单元回收的伏笔（JSON 数组） |
| created_at | TEXT | 创建时间 |
| updated_at | TEXT | 更新时间 |

**关键新增字段**：`cause_summary` 和 `effect_summary` —— 这两个字段是因果编排的锚点。

### 3.3 新增表：unit_causal_edges（单元因果边）

这是因果网络的核心——记录单元之间的因果关系。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | TEXT PRIMARY KEY | 边 ID |
| project_id | TEXT NOT NULL | 项目 ID |
| from_unit_id | TEXT NOT NULL | 因单元（前） |
| to_unit_id | TEXT NOT NULL | 果单元（后） |
| edge_type | TEXT | 因果类型（见下表） |
| description | TEXT | 因果关系描述 |
| strength | REAL | 因果强度 0-1（1=直接因果，0.3=微弱关联） |
| created_at | TEXT | 创建时间 |

**因果类型（edge_type）**：

| 类型 | 说明 | 示例 |
|------|------|------|
| direct | 直接因果 | A 直接导致 B |
| setup_payoff | 铺垫-回收 | A 埋伏笔，B 回收 |
| character_change | 人物变化 | A 中人物变化导致 B 中行为 |
| world_change | 世界观变化 | A 中世界变化导致 B |
| parallel | 并行线 | A 和 B 是两条并行线，最终汇合 |
| flashback | 插叙/回忆 | B 是 A 中提到的往事 |
| chekhov | 契诃夫之枪 | A 出现道具，B 用到 |

### 3.4 新增表：unit_causal_groups（因果群/剧情线）

把一组相关的因果单元打包成一条"剧情线"。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | TEXT PRIMARY KEY | 群 ID |
| project_id | TEXT NOT NULL | 项目 ID |
| name | TEXT | 剧情线名称（如"主线"、"感情线"、"副线A"） |
| color | TEXT | 标记颜色 |
| description | TEXT | 剧情线描述 |
| unit_ids | TEXT | 包含的单元 ID 列表（JSON 数组） |
| sort_order | INTEGER | 排序 |
| created_at | TEXT | 创建时间 |

## 四、编排师（Orchestrator）的新职责

### 4.1 从"执行写作"到"编排+写作"

| 维度 | 旧编排师 | 新编排师 |
|------|---------|---------|
| 工作对象 | 章节 | 故事单元 |
| 核心职责 | 调度 Agent 写一章 | 因果编排 + 调度 Agent 写单元 |
| 输入 | chapter_id + 章节大纲 | unit_id + 单元大纲 + 因果上下文 |
| 输出 | 写完的章节 | 写完的单元 + 更新后的因果网络 |

### 4.2 编排师的新工作流

```
1. 因果审查（Causal Review）
   ├─ 检查本单元的 cause_summary 是否与前一单元的 effect_summary 衔接
   ├─ 检查本单元要回收的伏笔是否已经埋设
   ├─ 检查本单元要埋设的伏笔是否合理
   └─ 如果有问题，先调整大纲再写

2. 上下文组装（Context Assembly）
   ├─ 拉取因果上游单元的关键信息
   ├─ 拉取本剧情线的历史
   ├─ 拉取全局 L1/L2 记忆
   └─ 组装成写作上下文

3. 单元写作（Unit Writing）
   └─ 跟现有的 9 步流程类似，但目标是写完整单元（不是单章）

4. 写后因果更新（Post-write Causal Update）
   ├─ 从写完的文本里提取实际埋设/回收的伏笔
   ├─ 更新本单元的 cause_summary / effect_summary
   ├─ 更新因果边（unit_causal_edges）
   └─ 同步到 L1/L2 记忆系统
```

### 4.3 编排师的新接口

```python
class Orchestrator:

    # ---- 旧接口（保留，兼容章节模式）----
    def run_chapter(self, project_id, chapter_id, ...) -> OrchestratorResult:
        """写一章（现有接口，完全保留）"""

    # ---- 新接口（单元模式）----
    def run_unit(self, project_id, unit_id, ...) -> UnitOrchestratorResult:
        """写一个完整单元（新主接口）"""

    def review_causality(self, project_id, unit_id) -> CausalReviewResult:
        """因果审查：检查本单元与前后单元的因果衔接"""

    def update_causal_graph(self, project_id, unit_id, draft_text) -> None:
        """从写完的文本里提取因果关系，更新因果网络"""
```

## 六、拆章流程的调整

### 6.1 拆章的触发时机

```
单元写作完成
    ↓
因果审查通过
    ↓
用户确认拆章
    ↓
unit_splitter 分析断章点
    ↓
用户确认/调整断章点
    ↓
执行拆章 → 创建章节
    ↓
单元-章节状态映射（unit_chapter_mapper）
    ↓
章节进入现有章节流程（编辑/潜文本/一致性/...）
```

### 6.2 拆章后，单元和章节的关系

- 单元：`status = "split"`，内容归档，不再修改
- 章节：拆出来的章节走正常章节流程
- 可以从章节反查来源单元（`chapter_briefs.unit_id`）

## 七、向后兼容策略

### 7.1 老项目怎么办？

**策略：双轨制，渐进式**

| 项目类型 | 大纲视图 | 写作方式 |
|---------|---------|---------|
| 新项目 | 单元视图（默认） | 单元写作 + 拆章 |
| 老项目 | 章节视图（默认） | 章节写作（现有方式） |
| 老项目（手动升级） | 可切换到单元视图 | 每章自动包一个"虚拟单元" |

### 7.2 虚拟单元升级路径

老项目想转单元模式时：
1. 每章自动创建一个虚拟单元（1:1 对应）
2. 虚拟单元的 `unit_type = "chapter"`
3. 用户可以选择把多个相邻的虚拟单元合并成一个真实单元
4. 合并后再重写/调整

### 7.3 编排师的双模式

- `run_chapter()` — 章节模式（保留，给老项目用）
- `run_unit()` — 单元模式（新主接口，给新项目用）

两个接口共用底层的 Agent 调度逻辑，只是输入输出不同。

## 十、总结

### 10.1 核心价值

1. **创作与发布解耦**：用单元创作，用章节发布，各取所需
2. **因果可见**：大纲不再是线性列表，能看到单元之间的因果关系
3. **编排师升级**：从"写手"变成"编辑+写手"，先审查因果再写
4. **灵活调整**：想加单元、删单元、调整顺序，都比改章节方便

### 10.2 与现有系统的关系

- 现有章节系统 **100% 保留**，作为下游发布层
- 现有编排师的 `run_chapter()` **完全保留**，老项目不受影响
- 单元模式是**新增的上游创作层**，不破坏任何现有功能
- 拆章器是**连接创作层和发布层的桥梁**
