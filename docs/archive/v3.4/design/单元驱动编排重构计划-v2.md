# 单元驱动编排重构计划 v2（整合三份外部评审）

## 概述

**目标**：废弃章节驱动双架构，打通单元写作流，建立 Event Diff + Exporter 解耦。

**产品定位**：AI 长篇网文创作引擎（Story Compiler）—— 不是 Story OS，不做操作系统，只做"把脑中的故事编译成可发布的章节"。

**核心原则**：
1. 内部永远只有 Unit，章节永远只是 Adapter/Exporter
2. 不让代码里出现 `if chapter else unit`
3. 老项目 Chapter 通过 Virtual Unit 包装进入 Story Engine
4. 不做 Event 自动交换顺序（网文不需要倒叙，会破坏伏笔锚点）
5. Story Graph 是未来壁垒（6-12 个月），现在只做数据沉淀

**当前问题**：
- `Orchestrator.run_chapter()` 是主入口，`run_unit()` 无人调

    def run_unit(

        project_id: str,
        unit_id: str,

        retention: Optional[float] = None,

## 验证步骤

1. **Virtual Unit 流程**：老项目 Chapter → Virtual Unit → `run_unit()` → 导出新 Chapter
2. **Event Diff 流程**：写完 Unit → 自动检测角色信任变化 → 写入 Event → Memory 检索读到 Event
3. **Exporter 流程**：Unit 写完 → 调 Exporter → 番茄 2500 字 / 起点 4000 字 不同输出
4. **Hook 自动检测**：Unit 中角色获得关键物品 → 自动 plant 钩子 → 后续 Unit payoff
5. **回滚一致性**：回滚到 Step 2 → Event 查询只返回 Step 2 之前的 Diff → 钩子也只保留 Step 2 之前的

---

## 风险与假设

**风险**：
1. **StoryTeller 回调设计**：`run_unit()` 多次调用 writer_fn，每次上下文不同，需确保 AI 输出连贯
2. **Event Diff 计算精度**：角色状态是 JSON 嵌套结构，diff 算法需处理嵌套对象
3. **Virtual Unit 性能**：老项目大量 Chapter 同时包装为 Virtual Unit 可能影响启动速度

**假设**：
1. 用户确认单元驱动为唯一模式（不保留章节驱动入口）
2. `unit_writing_service.run_unit()` 的 StepWriterFn 接口稳定
3. Event Diff 计算在 Unit 写作完成后自动触发（不阻塞写作流程）
