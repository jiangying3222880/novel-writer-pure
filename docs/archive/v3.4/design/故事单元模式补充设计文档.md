## 一、评审意见确认

### 1.1 v1.0 分析正确的部分（确认无误）

| 判断 | 评价 |
|---|---|
| 12张表与chapter强绑定 | ✅ 扫描完整，没漏 |
| 记忆核心L1-L4不用重设计 | ✅ 对，分层思想是正确的 |
| "单元是上游、章节是下游"的架构思路 | ✅ 这是关键洞察，方向正确 |
| 不是"重设计"而是"扩展时间锚点" | ✅ 这是核心结论，方向正确 |

**最值钱的一句话**：「单元模式不是要替代章节，而是在章节之上增加一个上游创作层」——这个定位对了，整个改造就有主心骨了。

### 1.2 v1.0 的三个核心问题

#### 问题1：低估了"单元拆章"的复杂度

v1.0 说"单元拆章时，把单元级的记忆、角色状态、压力等映射到章节级，拆章完成后现有章节级流程完全不变"。

这话听起来很美，但**映射逻辑本身是个大工程**，不是"小改"能盖过去的。具体难点：

- **记忆拆分**：一个单元里有5条记忆（承诺、伏笔、世界规则），拆成3章后，第2条记忆到底属于第1章还是第2章？需要文本定位或时间戳切分
- **角色状态快照**：单元入口/出口有状态，但中间拆了3章，每章的入口/出口状态怎么生成？要么AI补全，要么按比例插值——都不是免费操作
- **压力曲线**：一个单元一条压力，拆成3章后压力曲线会变成阶梯型，跟原来"每章一条"的连续性对不上
- **潜文本卡**：单元级一张卡，拆章后每章一张卡？还是共享？v1.0没说清楚

**判断**：这块不是"小改"，至少是**中等工作量**，而且是最容易出bug的地方。应该从 `story_unit_service.py` 里拆出来，单独设计成一个模块。

#### 问题2：`as_of_unit` 查询的语义边界没定义清楚

v1.0 说加 `as_of_unit` 参数，但没回答一个关键问题：

> **写作单元时，记忆应该截止到"上一单元的结尾"还是"本单元的开头"？**

这听起来像同一个时刻，但实际不是：
- 如果截止到上一单元结尾 → 本单元写作时拿不到本单元自己产生的记忆（比如本单元第2段刚立的承诺，第5段就查不到）
- 如果包含本单元已写部分 → 需要单元内的"段级时间戳"，不然没法区分先后

章节制下这个问题被掩盖了——因为一章是一次AI生成，内部不需要中途查记忆。但**单元如果是多段落、多次AI生成的**，这个问题就暴露了。

**判断**：需要明确单元内部的时间锚点机制，否则 `as_of_unit` 会变成一个语义模糊的接口。

#### 问题3："改动量小"这个结论过于乐观

v1.0 最后给的清单看着都是"加字段、加参数、加函数"，单看每一项确实小。但它漏算了两件事：

1. **数据迁移**：已有项目全是章节制数据，加 `unit_id` 字段后，老数据的 `unit_id` 填什么？NULL？还是自动给每章建一个虚拟单元？这决定了老项目能不能用新版本打开
2. **UI 的双视图**：v1.0 提了 `generate_tab` / `outline_tab` 有 `current_chapter_id`，但没说改成单元制后，UI 是"单元视图+章节视图"两个Tab，还是一个Tab里切换？这俩工作量差一个数量级

**判断**：真实工作量大概比 v1.0 估计的多 40-60%，主要在映射模块、数据迁移、UI双视图这三块。

## 二、v1.0 未覆盖的盲区

| 盲区 | 说明 | 严重度 |
|---|---|---|
| **钩子记忆** | 钩子记忆挂在章节上。改成单元制后，钩子是挂单元还是挂章节？如果挂章节，单元写作时钩子怎么触发？ | 🔴 高 |
| **导出/语音合成** | `exporter.py` / `tts_edge.py` 按章节导出。单元拆章前，能不能按单元导出？还是必须先拆章才能导出？ | 🟡 中 |
| **一致性检查** | `consistency.py` 逐章检查。单元写作阶段需不需要做一致性检查？如果需要，检查的粒度和锚点都得改 | 🟡 中 |
| **使用记录** | `usage_records` 的 `chapter_id` 是可选的。单元写作的token消耗记到哪？记到单元？那拆章后怎么分摊？ | 🟢 低 |
| **变更日志** | `chapter_change_log` 按章记录。单元写作阶段的变更要不要单独记？单元拆章后变更日志怎么衔接？ | 🟡 中 |

**钩子记忆那条是重点**——之前刚修过它的关键中断问题，改造时如果钩子锚点没跟着改对，之前的修复就白做了。

## 三、修订后的架构设计

### 3.1 新增模块：unit_chapter_mapper.py（单元-章节映射器）

**从 story_unit_service.py 中独立出来**，专门负责单元到章节的状态映射。

#### 职责范围

| 功能 | 说明 | 难度 |
|------|------|------|
| 文本切分 | 按断章点把单元正文切成多段 | ⭐ |
| 记忆映射 | 把单元级记忆分配到对应章节 | ⭐⭐⭐ |
| 角色状态插值 | 生成中间章节的角色状态快照 | ⭐⭐⭐ |
| 压力曲线平滑 | 从单元压力拆成每章压力 | ⭐⭐ |
| 潜文本卡拆分 | 单元级潜文本卡 → 章节级潜文本卡 | ⭐⭐ |
| 钩子映射 | 单元钩子 → 章节钩子 | ⭐⭐ |

#### 记忆映射策略（核心难点）

**原则**：能精确定位的精确分配，不能精确的保守处理。

| 记忆类型 | 映射策略 |
|---------|---------|
| **世界规则（L1）** | 全量复制到每一章（世界规则是全局的） |
| **故事弧（L1）** | 全量复制（弧是贯穿的） |
| **承诺/伏笔（L2）** | 根据文本位置精确分配：<br>1. 如果记忆有 ref_id 指向具体段落 → 分到该段落所在章节<br>2. 如果没有位置信息 → 分到第一章（保守策略，宁早勿晚） |
| **RAG 临时记忆（L3）** | 不迁移（L3是临时的，单元写完就该降级或遗忘） |
| **已遗忘（L4）** | 不迁移（已遗忘的不需要带过去） |
| **单元专属记忆** | 保留在单元上，不迁移到章节（这些是创作辅助信息，不是故事内容） |

#### 角色状态插值策略

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| **入口复制法** | 所有中间章节的入口状态 = 单元入口状态，最后一章出口 = 单元出口 | 简单快速，状态变化不大的单元 |
| **线性插值法** | 数值型属性（power_level等）按字数比例线性插值 | 数值属性变化 |
| **阶段标记法** | 在单元文本里用 `<!-- ROLE_STATE: {name: "林枫", power_level: "筑基期"} -->` 标记状态变化点，拆章时按标记切分 | 精确控制，需要手动标记 |
| **AI 生成法** | 让 AI 根据单元内容推断每章结束时的角色状态 | 最智能但成本高 |

**MVP 阶段用"入口复制法"**，后续版本再增加更高级的策略。

#### 压力曲线策略

- 单元级压力作为"基压"，复制到每一章的基础压力上
- 拆章后每章的 delta_pressure = 单元总变化量 / 章节数（平均分配）
- 后续可以做更精细的情绪曲线分析

### 3.2 单元内部时间锚点机制

#### 问题定义

`as_of_unit` 的语义：
- **默认语义**：截止到上一个单元的结尾（不含本单元内容）→ 用于写作前的上下文组装
- **扩展语义**：截止到本单元的某个进度点 → 用于单元内多次生成时

#### 设计方案：三级时间锚点

```
Level 0: 全局故事序
  story_order (单元级)
    ↓
Level 1: 单元内段落序
  unit_step (单元内的生成步/段落序号)
    ↓
Level 2: 章节序（拆章后）
  chapter_no
```

**Memory 表的时间锚点字段**：

| 字段 | 说明 | 粒度 |
|------|------|------|
| `story_order` | 故事内单元顺序 | 单元级 |
| `unit_id` | 所属单元 | 单元级 |
| `unit_step` | 单元内的步骤序号（可选） | 段级 |
| `chapter_id` | 所属章节（拆章后回填） | 章节级 |
| `chapter_no` | 章节序号（拆章后回填） | 章节级 |

**查询接口的语义**：

```python
# 1. 截止到上一单元结尾（写作前用，默认）
get_l1_l2_as_of_unit(project_id, unit_id, include_current=False)

# 2. 截止到本单元第 N 步（单元内多次生成用）
get_l1_l2_as_of_unit_step(project_id, unit_id, step)

# 3. 截止到某章（现有接口，完全不变）
get_l1_l2(project_id, as_of_chapter=chapter_id)
```

**MVP 阶段**：只做第 1 种（截止到上一单元结尾），第 2 种留到后续版本。

### 3.3 数据迁移策略

#### 核心问题：老项目怎么办？

**方案A：虚拟单元法（推荐）**

- 每个已有章节自动创建一个"虚拟单元"，1:1 对应
- 虚拟单元的 `unit_type = "chapter"`，`status = "split"`
- `story_order = chapter_no`
- 所有现有记忆/角色/压力等数据的 `unit_id` = 对应的虚拟单元 ID
- 用户看不到虚拟单元（UI 上隐藏），但数据层面保持一致
- 优点：完全向后兼容，老项目直接能用
- 缺点：数据里多了一层包装，有点冗余

**方案B：空单元法**

- 老项目的 `unit_id` 全为空字符串
- 查询时 `unit_id IS NULL OR unit_id = ''` 的记忆视为全局
- 优点：简单，数据干净
- 缺点：老项目用不了单元模式的功能，只能继续用章节模式

**方案C：手动迁移法**

- 提供一个迁移工具，用户手动选择把哪些章节合并成一个单元
- 优点：最干净，用户最清楚
- 缺点：用户体验差，老项目迁移成本高

**MVP 决策**：采用**方案B（空单元法）** 作为默认，原因：
1. 最简单，出bug概率最低
2. 老项目不受任何影响，继续用章节模式
3. 新项目可以选择用单元模式
4. 后续再加上"章节合并为单元"的工具作为可选升级路径

### 3.4 UI 双视图策略

#### 核心问题：怎么展示单元和章节的关系？

**方案A：两个独立 Tab（推荐，MVP 用这个）**

- `故事单元` Tab：管单元创作、排序、拆章
- `大纲管理` Tab：管分卷、章节、编辑（现有，完全不变）
- 优点：清晰，不混乱，两边互不干扰
- 缺点：用户需要在两个 Tab 之间切换

**方案B：大纲 Tab 里切换视图**

- 大纲 Tab 加一个切换按钮："章节视图 / 单元视图"
- 同一棵树，切换显示粒度
- 优点：集成度高
- 缺点：实现复杂，容易搞乱

**方案C：混合树视图**

- 分卷 → 单元 → 章节，三层树
- 单元可以展开看下面的章节
- 优点：最直观
- 缺点：改动最大，UI 最复杂

**MVP 决策**：采用**方案A（两个独立 Tab）**，原因：
1. 实现简单，风险低
2. 不破坏现有大纲 Tab 的任何功能
3. 用户可以选择用不用单元模式
4. 后续验证了价值再考虑方案B或C

## 四、盲区解决方案

### 4.1 钩子记忆（高优先级）

**策略：双轨制**

| 阶段 | 钩子挂在哪 | 触发时机 |
|------|-----------|---------|
| 单元写作阶段 | 挂在 `unit_id` 上 | 单元写作时，从截止到上一单元的钩子里触发 |
| 拆章后 | 同时挂 `unit_id` 和 `chapter_id` | 章节写作时，按章节触发（现有逻辑不变） |

**拆章时的钩子映射**：
- 单元级钩子 → 根据文本位置分配到对应章节
- 不能定位的 → 分到第一章
- `hook_id` 保持不变，只是增加 `chapter_id` 字段

### 4.2 导出/语音合成（中优先级）

**策略：拆章后才能导出**

- MVP 阶段：不支持按单元导出，必须先拆章
- 理由：导出和 TTS 都是面向最终发布的，发布单位是章节
- 后续可以加"按单元导出草稿"的功能，用于内部审阅

### 4.3 一致性检查（中优先级）

**策略：单元级检查 + 章节级检查，两套并存**

| 检查级别 | 触发时机 | 检查内容 |
|---------|---------|---------|
| 单元级 | 单元写完后 | 单元内部的一致性（前后矛盾、人设崩坏） |
| 章节级 | 拆章后/章节编辑后 | 章节间的一致性（现有逻辑不变） |

**MVP 阶段**：先不做单元级一致性检查，等核心功能稳定后再加。

### 4.4 使用记录（低优先级）

**策略：记到单元上，拆章后不分摊**

- 单元写作阶段的 token 消耗 → `usage_records.unit_id`
- 拆章后不做分摊，保持在单元上
- 统计时：总消耗 = 章节消耗 + 单元消耗
- 理由：分摊太复杂，而且价值不大，用户只关心总数

### 4.5 变更日志（中优先级）

**策略：单元变更单独记，拆章后不迁移**

- 单元写作阶段的变更 → `chapter_change_log.unit_id`（新增字段，已加）
- `chapter_id` 为空
- 拆章后不迁移变更历史
- 理由：变更日志主要用于回溯，单元级的变更保持在单元上就行
