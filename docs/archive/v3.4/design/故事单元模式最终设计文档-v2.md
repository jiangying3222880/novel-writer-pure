## 一、核心设计理念

### 1.1 一句话总结

> **单元是创作单位，章节是发布单位。先以单元创作完整故事，再在读者最有感觉的地方断章。**

### 1.2 三个核心洞察

1. **创作与发布解耦**：单元负责创作质量，章节负责发布体验
2. **双时间线分离**：故事时间（因果顺序）≠ 呈现时间（读者顺序），支持非线性叙事
3. **断章是设计出来的**：站在全局情绪曲线视角，精确选择每一刀下在哪里最痛

## 二、整体架构

### 2.1 三层架构

```
┌─────────────────────────────────────────────────────────┐
│                    创作层（上游）                         │
│  分卷(Book) → 故事单元(Unit) → 单元大纲(UnitBrief)       │
│                     ↑                                    │
│              编排师：因果编排 + 单元写作                   │
│         （双时间线 + 衔接类型 + 情绪曲线）                │
└──────────────────────────┬──────────────────────────────┘
                           │ 拆章（情绪曲线断章）
                           ▼
┌─────────────────────────────────────────────────────────┐
│                    聚合层（桥梁）                          │
│         分章规则配置 + 断章点分析 + 衔接打磨               │
└──────────────────────────┬──────────────────────────────┘
                           │ 导出
                           ▼
┌─────────────────────────────────────────────────────────┐
│                    发布层（下游）                         │
│        分卷(Book) → 章节(Chapter) → 章节大纲             │
│              现有系统完全不变                              │
│    （编辑 / 潜文本 / 一致性 / TTS / 导出）               │
└─────────────────────────────────────────────────────────┘
```

### 2.2 与现有系统的关系

- 现有章节系统 **100% 保留**，作为下游发布层
- 现有编排师 `run_chapter()` **完全保留**，老项目不受影响
- 单元模式是**新增的上游创作层**，不破坏任何现有功能

## 四、双时间线设计

### 4.1 核心概念

```
故事时间（story_order）：事件在故事世界里发生的先后顺序
    → 用于：因果网络、写作时上下文组装、伏笔管理

呈现时间（present_order）：读者阅读时看到的先后顺序
    → 用于：单元排序、拆章、章节编号
```

### 4.2 非线性叙事示例

```
故事时间:  A(铺垫) → B(发展) → C(揭秘) → D(高潮)
呈现时间:  A(铺垫) → B(发展) → D(高潮) → C(回想)
                                        ↑
                                   flashback类型
```

**D 的因果上游是 C**（写作时需要知道 C 里发生了什么），但**呈现上 D 在 C 前面**（读者先看到高潮，再通过回想了解原因）。

### 4.3 系统行为

| 操作 | 按 story_order | 按 present_order |
|------|---------------|-----------------|
| 写作时上下文组装 | ✅ 拉取因果上游 | ❌ 不按呈现顺序 |
| 因果边建立 | ✅ 按故事时间 | ❌ |
| 单元列表默认排序 | ❌ | ✅ 默认按呈现顺序 |
| 拆章 | ❌ | ✅ 按呈现顺序拆 |
| 伏笔管理 | ✅ 按故事时间埋/收 | ❌ |
| UI 视图切换 | 可切换到故事时间视图 | 默认视图 |

### 4.4 连贯性检查

调整呈现顺序后，自动检查：
- ⚠️ 呈现顺序在因果上游之前的单元 → 自动标记为 flashback
- ⚠️ 伏笔回收单元在埋设单元之前（呈现上）→ 提示用户
- ✅ 故事时间链完整（没有因果断裂）

## 五、情绪曲线断章设计

### 5.1 核心理念

> **断章不是按字数切，是在读者最有感觉的时候下刀。**

### 5.2 六种断章位模式

| 模式 | 读者心理 | 痛感等级 | 检测信号 |
|------|---------|---------|---------|
| 揭示型 | "竟然是？！" | ⭐⭐⭐⭐⭐ | 反转/揭秘句式 |
| 危机型 | "别！危险！" | ⭐⭐⭐⭐ | 突发危机句式 |
| 选择型 | "选A还是B？" | ⭐⭐⭐⭐ | 抉择/犹豫句式 |
| 情绪峰值 | "太燃了！" | ⭐⭐⭐⭐ | 情绪词+感叹号密度 |
| 悬念前置 | "然后呢？" | ⭐⭐⭐ | 悬念预告句式 |
| 场景收束 | "下一个场景？" | ⭐⭐ | 环境/时间收尾 |

### 5.3 断章痛感公式

```
断章痛感 = （读者投入度 × 问题紧迫度）÷ 答案可得性

- 读者投入度：角色/剧情的关心程度
- 问题紧迫度：是否立刻想知道答案
- 答案可得性：下一章能不能看到（不能太远，不能太近）
```

### 5.4 断章策略（split_strategy）

| 策略 | 适用 | 断章偏好 |
|------|------|---------|
| 爽文模式 | 升级流/爽文 | 高潮后断（先爽再勾） |
| 悬疑模式 | 悬疑/推理 | 揭秘前断（最痛） |
| 感情模式 | 言情/感情线 | 情感爆发前断 |
| 节奏模式 | 快节奏文 | 小高潮密集断 |
| 平稳模式 | 文青/慢热 | 场景收束断 |
| 自动（默认） | 通用 | 按痛感评分排序 |

### 5.5 拆章器工作流

```
1. 情绪曲线分析（关键词密度 + 标点密度，不用AI）
   → 画出单元内情绪高低起伏

2. 断章模式匹配（正则匹配6种模式）
   → 每个候选位置打分：基础分 × 位置系数

3. 候选断章点排序
   → 按痛感等级排序，给用户呈现断章报告

4. 人工确认/调整
   → 用户看断章报告，选最优断点

5. 执行拆章
   → 按确认的断点切分，创建章节
```

### 5.6 断章报告示例

```
📍 候选断章点 #1（位置: 3200字，痛感: ★★★★★）
  类型：揭示型断章
  原文片段：
    他猛地抬头，看向墙上的那幅画。
    画里的人，竟然和他长得一模一样。
  推荐理由：身份揭秘，好奇心拉满
  风险提示：下一章开头需要接住这个揭秘

📍 候选断章点 #2（位置: 2800字，痛感: ★★★☆☆）
  类型：情绪峰值断章
  原文片段：
    "我喜欢你。"
    她的声音很轻，却像惊雷一样在他耳边炸开。
  推荐理由：情感爆发，情绪高点
```

## 六、编排师（Orchestrator）升级

### 6.1 新增接口

```python
class Orchestrator:
    # 旧接口（保留）
    def run_chapter(self, project_id, chapter_id, ...) -> OrchestratorResult

    # 新接口（单元模式）
    def run_unit(self, project_id, unit_id, ...) -> UnitOrchestratorResult
    def review_causality(self, project_id, unit_id) -> CausalReviewResult
    def update_causal_graph(self, project_id, unit_id, draft_text) -> None
```

### 6.2 单元写作工作流

```
1. 因果审查（Causal Review）
   ├─ 检查 cause_summary 与前一单元 effect_summary 衔接
   ├─ 检查要回收的伏笔是否已埋设
   ├─ 检查要埋设的伏笔是否合理
   └─ 检查呈现顺序与因果顺序的一致性

2. 上下文组装（Context Assembly）
   ├─ 拉取因果上游单元的关键信息（按 story_order）
   ├─ 拉取本剧情线的历史
   ├─ 拉取全局 L1/L2 记忆
   ├─ 加载入口状态快照
   └─ 组装成写作上下文

3. 单元写作（Unit Writing）
   └─ 9步流程（同现有，但目标是写完整单元）

4. 写后因果更新（Post-write Causal Update）
   ├─ 提取实际埋设/回收的伏笔
   ├─ 更新 cause_summary / effect_summary
   ├─ 更新因果边
   ├─ 生成出口状态快照
   └─ 同步到 L1/L2 记忆
```

## 七、单元-章节状态映射

### 7.1 独立模块：unit_chapter_mapper.py

从 story_unit_service.py 中独立，专门负责拆章时的状态迁移。

### 7.2 映射策略

| 数据类型 | 映射策略 |
|---------|---------|
| 世界规则（L1） | 全量复制到每章 |
| 故事弧（L1） | 全量复制 |
| 承诺/伏笔（L2） | 根据文本位置精确分配，不能定位的分到第一章 |
| RAG临时（L3） | 不迁移 |
| 已遗忘（L4） | 不迁移 |
| 单元专属记忆 | 保留在单元上，不迁移 |
| 角色状态 | 入口复制法（MVP），后续支持插值/AI生成 |
| 压力曲线 | 单元压力作为基压，平均分配到每章 |
| 潜文本卡 | 单元级保留，拆章后每章可新建章节级卡 |

| 创作自由度 | 必须按时间线 | 可跳写、可并行、可重组 |
| 叙事结构 | 只能线性 | 倒叙/插叙/并行/POV切换 |

| 断章精度 | 凭感觉+字数 | 情绪曲线+断章模式 |
| 剧情调整 | 牵一发而动全身 | 改单元不影响全局 |
| 伏笔管理 | 逐章追踪 | 单元级设计，全局视角 |
| 上下文可控 | 黑盒 | 白盒配置 |
| 错误隔离 | 沿章节累积 | 单元级隔离 |
