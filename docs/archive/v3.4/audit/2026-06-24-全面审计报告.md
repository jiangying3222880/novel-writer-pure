## 二、架构分析

### 2.1 分层结构 ✅ 设计清晰

```
app/
├── ui/              # L3 表现层 - PySide6 界面
├── services/        # L2 业务服务层 - 核心业务逻辑
│   └── writing/     #   - 写作相关子模块（G系列）
├── ai/              # L1 AI层 - 模型接入与调度
├── agents/          # L1 Agent层 - 多智能体协作
├── core/            # L0 核心层 - 基础设施 + shim 兼容层
├── db/              # 数据层 - SQLite 封装
├── knowledge/       # 知识库 - BM25 + 向量检索
├── workflow/        # 工作流 - 改稿信号系统
└── extension_api/   # 扩展 API - HTTP 桥 + 插件加载
```

**优点**:
- 分层职责明确，自上而下依赖
- Protocol 接口契约设计良好（`app/core/interfaces.py`）
- IoC 容器支持按 Protocol 注入（`app/core/container.py`）

**问题**:
- `app/core/` 下存在大量 **shim 兼容层**（如 `core/prompt_assembler.py` 仅是 re-export），实际代码已迁至 `app/services/writing/`
- 历史遗留的模块迁移痕迹明显，增加了理解成本

### 2.2 核心数据流 ✅ 设计完整

7步写作工作流编排合理（`app/services/writing_engine.py`）：

```
记忆拼装 → 反AI味 → 压力决策 → RAG检索 → 写作 → 评估 → 落库
```

## 三、核心模块审计

### 3.1 AI 引擎与路由系统 ⚠️ 双轨并行

**现状**: 存在两套独立的 AI 调用入口：

| 系统 | 文件 | 状态 |
|------|------|------|
| AIEngine | `app/ai/engine.py` | 主要使用，服务层调用 |
| LLMRouter | `app/ai/router.py` | 功能更全（缓存/并行/降级链） |
| RealLLMClient | `app/services/router/real_client.py` | 第三套包装层 |

**问题**:
- **功能重叠**: 两者都有重试+降级逻辑
- LLMRouter 能力更强（二级缓存 + 并行调度 + SequentialFallbackChain），但实际业务用的是 AIEngine
- 存在 `RealLLMClient` 作为第三套包装层

**建议**: 统一到 LLMRouter，逐步废弃 AIEngine

### 3.2 写作引擎 ✅ 功能完整

`app/services/writing_engine.py` 是核心：
- 7步编排逻辑清晰
- 支持取消（EngineCancelledError）
- 流式输出回调
- Mock 模式自动检测（NW_AI_MOCK 环境变量）

### 3.3 数据库层 ✅ 迁移系统完善

- 28个 SQL 迁移文件（版本号 005-032）
- 迁移器支持幂等执行、事务保证（`app/db/migrator.py`）
- 25+ 个数据模型（`app/db/models.py`）

**问题**:
- 两套数据库连接机制：`app.db.connection`（单例）和 `app.services.db`（thread-local）
- 测试中发现 UI 测试的 DB 路径初始化有问题

### 3.4 Agents 系统 ⚠️ 初级阶段

`app/agents/orchestrator.py` 将军模式：
- 6个辅助Agent（StoryTeller/Editor/Critic/Retriever/MemoryKeeper/PressureWatcher）
- 支持评估门控改稿循环
- 追读率动态调整

**问题**:
- 6个 helper Agent 中部分还是 mock 或半实现状态
- 与 writing_engine 的7步工作流功能高度重叠，定位需明确

### 3.5 风格指纹系统 ⚠️ 模型混乱

存在三套模型：

| 模型 | 位置 | 状态 |
|------|------|------|
| StyleFingerprint（5维） | `db/models.py` L334 | **DEPRECATED** |
| AuthorFingerprint（6维） | `db/models.py` L304 | 新（作者层） |
| BookFingerprint（4维） | `db/models.py` L320 | 新（作品层） |

**问题**:
- 迁移了但没完全迁完，prompt_assembler 等关键路径可能还在用旧维度名
- style_learner 和 ai_body_gen 各有一套风格提取算法（重复实现问题）

### 3.6 插件系统 ❌ 已移除但有残留

**现状**:
- `app/plugins/` 目录已不存在
- 但 `smoke_m1_core.py` 还在 import `app.plugins` → **测试失败**
- 部分代码中仍有 plugin 相关函数（`is_plugin_unlocked` 等）

## 六、主要风险与问题汇总

### 🔴 高风险问题

1. **测试失败**: 多个核心冒烟测试不通过，回归验证能力下降
2. **插件系统残留**: 移除了但测试和部分代码未同步清理
3. **AI调用入口不统一**: AIEngine / LLMRouter / RealLLMClient 三套并存

### 🟡 中风险问题

4. **风格指纹模型迁移未完成**: 新旧三套模型并存，prompt 注入可能不一致
5. **两套 DB 连接**: `app.db.connection` vs `app.services.db` 职责不清
6. **core 层 shim 过多**: 增加理解成本和维护负担
7. **Agents 与 WritingEngine 功能重叠**: 定位不明确

### 🟢 低风险/优化项

8. `services/__init__.py` 导出的服务不全（很多新服务没加进去）
9. 部分测试文件在 `run_all.py` 的 SMOKES 列表中不存在（如 smoke_m6_market_ui）
10. docs 目录内容单薄

## 八、总结

**整体评价**: 这是一个**功能丰富、架构设计合理但历史包袱较重**的项目。

- ✅ **做得好的**: 分层架构清晰、7步工作流设计合理、迁移系统完善、主题系统规范、测试隔离机制
- ⚠️ **需要注意**: 多套类似系统并存（AI引擎/风格指纹/DB连接）、插件移除有残留、测试有失败
- 🎯 **建议优先级**: 先修测试保证质量基线 → 再统一AI入口和风格指纹 → 最后清理历史遗留
