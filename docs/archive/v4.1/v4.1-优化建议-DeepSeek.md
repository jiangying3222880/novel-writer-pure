# v4.1 优化建议（基于 DeepSeek 反馈）

> 日期：2026-07-07
> 来源：DeepSeek 对项目流程的深度评审
> 定位：从"技术 Demo"走向"真正可用工具"的卡点分析

---

## 一、核心问题

> 你的流程在"纯逻辑推导"上非常完美，但**严重缺乏"人工干预节点"和"增量操作模式"**。
> 现在的流程像一条"全自动香肠生产线"，但对于小说家来说，他们需要的是**"数控机床"**——能随时暂停、手动微调刀头、只修改局部纹路，而不是每次都把钢材回炉重铸。

---

## 二、5 个关键优化点

### 优化 1：草稿逆向导入（输入流程）

**现状问题**：
- 项目高度依赖结构化的 JSON/YAML 定义（单元、角色属性、情节节点）
- 作者必须先想好一切，再"翻译"成代码对象
- 实际痛点：绝大多数作者是"混乱生长型"——先写 5000 字碎碎念，再慢慢提炼大纲

**落地方案**：

新增 `draft_importer.py`：
```
输入: .txt / .md 草稿文件
  ↓ NER（命名实体识别）提取角色
  ↓ 摘要生成大纲
  ↓ 自动创建 Unit + Evidence
输出: 结构化的 Unit 列表
```

**核心价值**：降低前 10 分钟的上手弃用率——"先有文字，后有结构"。

---

### 优化 2：冲突消解日志 + 人工仲裁（指南生成流程）

**现状问题**：
- Guide Graph 自动检测冲突并消解，对用户透明
- 当 AI 自动把作者精心设计的"反派人设微调"判定为冲突并"智能抹平"时，作者会极度愤怒且不知所措

**落地方案**：

1. **强制输出冲突消解日志**：
   - 每次冲突消解生成 `.conflict_log` 文件
   - 用自然语言写明：*"第 3 章的 Guide A 与第 7 章的 Evidence B 冲突，系统采用了方案 C，理由如下……"*

2. **人工仲裁断点**：
   - 在流程中增加 `--wait-for-approval` 模式
   - 当冲突等级高于阈值时，流程暂停
   - 弹窗提醒作者做二选一，而不是闷头跑完整个编译流程
   - 对于长篇小说，一次错误的自动消解足以毁掉后续 20 章

**核心价值**：这是"Guidance 而非 Constraint"原则的具体体现。

---

### 优化 3：增量补丁而非全量重编（编译器流程）

**现状问题**：
- Story Compiler 能分析影响范围，但作者只改了一个配角的名字
- 编译器为了保持一致性，可能要重新生成涉及该名字的 15 个章节
- 不仅浪费 API 费用，更可怕的是**生成质量不稳定**——本来写好的第 8 章重生成后可能就废了

**落地方案**：

1. **放弃"自动重编"，改为"影响预览 + 增量补丁"**：
   - 编译器不要直接改写源文件
   - 当检测到影响范围时，先输出 `patch_preview.md`
   - 只高亮显示"哪些句子将被替换"

2. **作者确认后，只替换指定句子**：
   - 不动其他 99% 的内容
   - 这才是作者敢用的"修订模式"，而不是"随机重写模式"

**核心价值**：这是"数控机床"而非"香肠生产线"。

---

### 优化 4：常识与时间线断言（验证流程）

**现状问题**：
- 44 项验证测试通过，主要验证数据完整性和类型
- 验证通过不代表故事"不崩"——人物上一章死了下一章复活，验证层检测不出来

**落地方案**：

新增"常识与时间线断言"验证模块：
```
检查项:
├── 死亡角色名单 vs 当前章节出场人物 → 重叠度检查
├── 日期连续性检查
├── 天气连续性检查
├── 位置连续性检查
└── 不通过则编译失败并报错（不是带着错误继续走完流程）
```

**核心价值**：验证通过 ≠ 故事不崩。

---

### 优化 5：反向编译（输出流程）

**现状问题**：
- 输出最终的整章文本
- 作者拿到文本后，必然要手动大改
- 改完之后，这些改动如何**反向同步**回 Evidence 库？
- 如果不同步，下一次编译又会把作者的修改覆盖掉

**落地方案**：

新增"反向编译（Reverse Compile）"流程：
```
作者在编辑器里修改了生成的章节
  ↓ CLI 命令: reverse_compile
  ↓ 扫描修改过的段落
  ↓ 增量更新 evidence_ids 的权重值（调高权重 = 作者认可）
  ↓ 自动拆分出新的 Unit
  ↓
实现: AI 生成 → 人类润色 → 知识库固化
```

**核心价值**：这是项目能否长用的命门。

---

## 三、总结：v4.1 核心目标

> **让作者在流程中任何一步停下来修改，修改后不必重跑全流程。**

做到这一点，这个项目就能从"极客玩具"跃升为"生产力工具"。

## 六、优化 6：已有创作内容导入（新增）

> 基于用户实际反馈：原有的大纲、设定、角色等无法导入进项目

### 现状问题

现有导入能力：
| 功能 | 支持格式 | 说明 |
|------|----------|------|
| 项目导入 | .nwp | 整个项目包 |
| 设定导入 | .md/.json | 小说设定 |
| 大纲导入 | .md/.json | 章节大纲 |
| 角色导入 | JSON | 角色卡片 |
| 世界观导入 | .md/.json | 世界观设定 |
| 知识库导入 | .txt/.md | 知识文件 |

**缺少的**：
- ❌ 故事结构从纯文本导入（.txt/.md → Unit + Evidence）
- ❌ 批量单元导入
- ❌ 从其他写作工具迁移（如 Scrivener、Word、WPS）

### 实际痛点

作者已经有大量创作内容（大纲文档、角色设定表、世界观笔记），但：
1. 这些内容格式各异（Word/Markdown/纯文本/Excel）
2. 手动重新输入耗时耗力
3. 导入后需要手动整理成系统要求的结构

### 落地方案

#### 方案 A：结构化文档导入

支持从 Markdown 文档自动识别并导入：

```
输入: .md 文件（按特定格式编写）
  ↓ 自动识别章节结构（## 第N章 / ### 角色 / ### 世界观）
  ↓ 解析为 Unit / Character / World 数据
  ↓ 导入到项目
```

**支持的文档格式**：
```markdown
# 小说标题

## 第一章：觉醒
内容...

## 第二章：试炼
内容...

## 角色设定
### 林凡
- 身份：修仙者
- 性格：坚韧

## 世界观
### 修仙体系
- 炼气 → 筑基 → 金丹...
```

#### 方案 B：批量单元导入

支持从 JSON/CSV 批量导入单元：

```json
[
  {
    "title": "觉醒",
    "synopsis": "主角发现修仙天赋",
    "unit_type": "setup",
    "content": "正文内容..."
  },
  {
    "title": "试炼",
    "synopsis": "主角参加入门测试",
    "unit_type": "battle",
    "content": "正文内容..."
  }
]
```

#### 方案 C：其他工具迁移

支持从常见写作工具导出并导入：
- **Scrivener**：导出为 .docx 或 .rtf → 解析导入
- **Word/WPS**：直接读取 .docx → 解析章节结构
- **纯文本**：按分隔符切分 → 导入为单元

### 实现文件

```
新建: app/services/content_importer.py
├── import_from_markdown(file_path) → ImportResult
├── import_from_json(file_path) → ImportResult
├── import_from_docx(file_path) → ImportResult
├── import_from_text(text, format) → ImportResult
└── batch_import_units(units_data) → ImportResult

新建: app/ui/widgets/import_wizard.py
├── 文件选择
├── 格式识别
├── 预览导入内容
├── 确认导入
└── 导入进度
```

### 核心价值

> **让作者的已有创作内容无缝迁移到新系统，而不是从零开始。**

这是"从极客玩具到生产力工具"的关键一步——如果作者必须手动重新输入所有内容，他们不会用这个工具。

## 八、优化 7：对话式创建项目（灵感捕捉）

> 基于用户实际场景：有灵感时如何快速创建项目

### 现状问题

- 传统方式需要填写表单（项目名、题材、设定等）
- 作者有灵感时往往是碎片化的想法，不想填表
- 从灵感 → 结构化项目的过程太慢，灵感会消散

### 实际场景

```
用户: "我想写一个修仙小说，主角是个废柴，但体内藏着上古神器"
系统: 自动创建项目，识别出：
  - 题材: 修仙
  - 主角: 废柴体质 + 上古神器
  - 核心冲突: 废柴 vs 神器的矛盾
  - 建议单元: 觉醒 → 试炼 → 揭秘 → 高潮
```

### 落地方案

#### 对话式创建流程

```
用户打开"新建项目"
  ↓ 选择"对话创建"
  ↓ 用户输入灵感（自然语言）
  ↓ AI 分析提取：
  ├── 题材类型
  ├── 核心设定
  ├── 角色信息
  ├── 情节走向
  └── 初始单元建议
  ↓ 生成项目草稿
  ↓ 用户确认/修改
  ↓ 项目创建完成
```

#### 对话界面设计

```python
class ConversationCreationDialog:
    """对话式项目创建."""
    
    def __init__(self):
        # 左侧: 对话区（用户输入 + AI 回复）
        # 右侧: 实时预览（提取的设定/角色/单元）
    
    def on_user_message(self, message: str):
        """处理用户输入."""
        # 1. AI 分析提取结构化信息
        # 2. 更新右侧预览
        # 3. 生成 AI 回复（确认/追问）
    
    def on_confirm(self):
        """用户确认创建."""
        # 1. 从对话中构建项目数据
        # 2. 调用 project_service.create()
        # 3. 自动创建初始单元
```

### 核心价值

> **让灵感在 30 秒内变成项目，而不是 30 分钟的表单填写。**

## 九、优化 8：单元池 + 分层知识库（范式转变）

> 基于用户实际需求：从"逐字写"到"拼装写"的范式转变

### 核心理念

> **作者只规划灵感和主线剧情，系统从单元池中拼装小说。**

传统写作：作者逐字逐句写 → 耗时耗力
单元池模式：作者规划灵感 + 主线 → 系统从池中选取/生成单元 → 拼装成完整小说

### 架构设计

```
用户输入
├── 灵感描述（一句话/一段话）
├── 主线剧情（大纲/分卷规划）
└── 风格偏好（题材/文风/节奏）
        ↓
    编排Agent
    ├── 从知识库获取编排技巧
    ├── 分析主线结构
    ├── 规划单元序列
    └── 决定哪些单元需要新写
        ↓
    写作Agent
    ├── 从知识库获取写作技巧
    ├── 从单元池选取相似单元
    ├── 参考范本进行创作
    └── 生成新单元或修改现有单元
        ↓
    单元池
    ├── 存储所有已创作的单元
    ├── 按题材/类型/情绪/长度分类
    └── 支持检索和拼装
        ↓
    完整小说
```

### 单元池设计

#### 单元格式

```json
{
  "unit_id": "uuid-xxx",
  "title": "觉醒",
  "genre": "仙侠",
  "type": "setup",
  "length": 1000,
  "emotion_tags": ["期待", "神秘", "紧张"],
  "plot_tags": ["开篇", "伏笔埋设", "主角亮相"],
  "characters": ["林凡", "慕容雪"],
  "content": "正文内容...",
  "quality_score": 0.85,
  "usage_count": 12,
  "last_used": "2026-06-01"
}
```

#### 单元分类维度

| 维度 | 示例 | 用途 |
|------|------|------|
| 题材 | 仙侠/都市/玄幻/言情/悬疑 | 按题材筛选 |
| 类型 | setup/battle/reveal/climax/transition | 按剧情节奏筛选 |
| 情绪 | 期待/紧张/感动/爽/虐 | 按情绪曲线筛选 |
| 长度 | 短(500-1000)/中(1000-3000)/长(3000+) | 按字数筛选 |
| 功能 | 开头/过渡/高潮/结尾/番外 | 按功能位置筛选 |

### 拼装流程

```
1. 用户输入：灵感 + 主线
   "写一个修仙小说，主角废柴逆袭，主线是宗门大比→秘境探险→最终决战"

2. 编排Agent分析：
   ├── 识别题材：仙侠
   ├── 识别主线阶段：铺垫→发展→高潮→结局
   ├── 规划单元序列：10-15个单元
   └── 判断：哪些单元可以从池中选取，哪些需要新写

3. 单元池检索：
   ├── 检索"仙侠+setup"单元 → 找到3个候选
   ├── 检索"仙侠+battle"单元 → 找到5个候选
   ├── 检索"仙侠+climax"单元 → 找到2个候选
   └── 返回候选列表供编排师选择

4. 编排师决策：
   ├── 选取合适的单元
   ├── 调整单元顺序
   ├── 确定需要新写的单元
   └── 生成完整大纲

5. 写作Agent执行：
   ├── 对需要新写的单元，参考知识库技巧创作
   ├── 对选取的单元，进行微调适配
   └── 生成完整小说
```

### 核心价值

> **从"逐字写"到"拼装写"——作者只需规划灵感和主线，系统负责执行。**

这是写作工具的范式转变：作者从"写作者"变成"策划者"，AI从"辅助者"变成"执行者"。

## 十、优化 9：知识库分区 + Agent 专属知识

> 基于用户实际需求：不同 Agent 需要不同的知识库支持

### 现状问题

- 现有知识库是扁平的，所有内容混在一起
- 编排师需要"剧情编排技巧"，但和"战力体系"混在一起
- 写作Agent需要"描写手法"，但找不到相关知识
- 知识库没有按 Agent 职责分区

### 知识库分区设计

```
知识库/
├── 编排师专区/ (参考: webnovel-writing skill 的 concept_planning + volume_outline + plot_logic)
│   ├── 剧情编排方案/
│   │   ├── 三幕式结构模板
│   │   ├── 英雄之旅模板
│   │   ├── 起承转合模板
│   │   └── 多线并行编排技巧
│   ├── 节奏控制/
│   │   ├── 快节奏写法
│   │   ├── 慢热铺垫技巧
│   │   └── 高潮设置方法
│   ├── 伏笔管理/
│   │   ├── 埋伏笔技巧
│   │   ├── 回收伏笔时机
│   │   └── 伏笔密度控制
│   └── 结构模板/
│       ├── 黄金三章结构
```

### Agent 知识访问权限

| Agent | 可访问知识库 | 用途 |
|-------|-------------|------|
| 编排师 (Orchestrator) | 编排师专区 + 通用知识库 | 学习编排技巧，参考世界观设定 |
| 写作Agent (StoryTeller) | 写作Agent专区 + 项目专属知识库 | 学习写作手法，参考已有内容 |
| 评估Agent (Editor/Critic) | 通用知识库 + 项目专属知识库 | 检查一致性，参考设定 |
| 记忆Agent (Memory) | 全部知识库 | 检索相关信息 |

### 实现方案

```python
class KnowledgePartition:
    """知识库分区管理."""
    
    PARTITIONS = {
        "orchestrator": ["编排师专区", "通用知识库"],
        "writer": ["写作Agent专区", "项目专属知识库"],
        "editor": ["通用知识库", "项目专属知识库"],
        "memory": ["*"],  # 全部
    }
    
    def get_knowledge_for_agent(self, agent_role: str, project_id: str) -> list[dict]:
        """获取指定 Agent 可访问的知识."""
        partitions = self.PARTITIONS.get(agent_role, ["通用知识库"])
        knowledge = []
        for partition in partitions:
            if partition == "项目专属知识库":
                knowledge.extend(self._load_project_knowledge(project_id))
            elif partition == "*":
                knowledge.extend(self._load_all_knowledge())
            else:
                knowledge.extend(self._load_partition(partition))
        return knowledge
```

### 核心价值

> **让每个 Agent 都有"专业领域知识"，而不是所有 Agent 共享同一个扁平知识库。**

编排师学习编排技巧，写作Agent学习描写手法，评估Agent学习检查标准——各司其职，各取所需。

### 知识整理原则（重要）

> **不是直接迁移原始文件，而是整理成 Agent 可快速理解的格式。**

#### 为什么不能直接迁移？

1. **原始文件太冗长** — 人物人设单个文件 68 万字，Agent 无法快速检索
2. **格式不适合 AI** — 散文式描述，缺乏结构化标签
3. **缺乏优先级** — 所有内容平等，Agent 不知道哪些更重要
4. **缺乏关联** — 角色设定和场景描写是分开的，Agent 无法关联

#### 整理后的格式

**原始格式（给人看）**：
```markdown
## 仙侠角色设定
修仙者通常分为以下几个境界：炼气期、筑基期、金丹期、元婴期...
每个境界的特点是...
常见突破方式有...
```

**整理后格式（给 Agent 看）**：
```json
{
  "genre": "仙侠",

  "tags": ["修仙", "境界", "突破"],

    "realm_system": ["炼气", "筑基", "金丹", "元婴", "化神", "渡劫"],
```

#### 整理流程

```
1. 分类提取
   ├── 按题材分类（仙侠/都市/玄幻/言情...）
   ├── 按用途分类（角色/场景/桥段/模板）
   └── 按 Agent 分区（编排师/写作Agent/通用）

2. 结构化转换
   ├── 散文 → JSON/YAML 结构
   ├── 添加标签（tags）
   ├── 添加优先级（priority）
   └── 添加用途说明（usage）

3. 精炼压缩
   ├── 68万字 → 每个题材 5-10KB 核心知识
   ├── 提取关键模式，去除冗余示例
   └── 生成可快速检索的索引

4. 建立关联
   ├── 角色模板 ↔ 场景描写（同一题材关联）
   ├── 剧情桥段 ↔ 框架模板（结构化关联）
   └── 跨题材共性提取
```
