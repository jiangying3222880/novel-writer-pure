## 一、核心判断（One-Sentence Truth）

> **v4.0 的根本问题不是"缺什么"，而是"做完了什么却没接上"。**
> 
> 项目 81k 行代码、60+ 文档沉淀、44/44 + 50/50 + 147/147 验证通过 —— 但用户实际跑起来，用的还是 v3.4 时代的 1131 行老 Orchestrator。

**翻译成一行命令**：

```bash
# 把 story/ 包真正接进 orchestrator，把 app/agents/ 顶层坏掉的 5 个文件删掉，
# 把 acceptance_checklist 的"假完成陷阱"逐条变真。
# 然后停止一切新抽象。
```

## 三、v4.0 的隐藏真相

### 3.1 v4.0 的 Story Compiler 从一开始就没集成

`v4_0_completion_report.md` 自承：

> ### 4.1 Story Compiler 未集成  
> **现状**: `analyze_impact()` 实现了，但 Orchestrator 未调用  
> **影响**: 用户修改 Unit 后，不会自动提示影响范围  
> **后续**: v5.0 集成到 Orchestrator + UI 展示  

但**v4.0 acceptance_checklist**（来自外部审计员）的措辞更尖锐：

> 表建了但全库零 INSERT（当前现状就是死骨架，必须打破）  
> service 写好了但 orchestrator 没有任何调用点  
> `analyze_split_points / split_unit / preview_split` 仍是死代码（本次审计发现它们当前零调用）

**这是一个典型"完成 ≠ 可用"陷阱**——v4.0 的模块都建好了，测试都能跑，但**没有进入用户路径**。

### 3.2 v3.4 的 8 个真实 UI bug 中，至少 3 个模式延续到了 v4.0

`2026-06-29 手动测试问题.md` 列了 8 个 v3.4 的 UI bug：

- 角色管理 tab：导入只能解析人名（→v4.0 角色管理**仍有问题**：`smoke_new_project_progress` 失败）
- 大纲管理 tab：保存/删除灰色、保存没测试（→v4.0 `writing_engine` 模块 **整体未集成**）
- 日志查看 tab 看不到终端报错（→v4.0 大量 `except Exception: pass` 主动吞错）

### 3.3 v3.4 审计报告说的问题，v4.0 没修

v3.4 `2026-06-24-全面审计报告.md` 列出 **8 大问题**：

| v3.4 问题 | v4.0 状态 |
|---|---|
| 测试失败 | ⚠️ **更严重**：5 个 Agent 文件全坏 + 3 处 API 失效 |
| 插件残留 | ✅ 真的删了 |
| AI 引擎三套并存 | ⚠️ 没解决，但被 56 个 services 掩盖 |

### 3.7 真实代码 Bug（需立即修复）

#### Bug #1：`app/ui/widgets/collapsible.py:165` — f-string 错误

```python
# ❌ 错误：内部 { background: {surface_bg()}; } 把 { background 当成表达式
self._body.setStyleSheet(f"QWidget#collapsibleBody { background: {surface_bg()}; }")
# 导致 NameError: name 'background' is not defined

# ✅ 应改为（双花括号转义）
self._body.setStyleSheet(f"QWidget#collapsibleBody {{ background: {surface_bg()}; }}")
```

**影响**：`smoke_ui_widgets.py` 失败，`CollapsiblePanel` 完全不可用 → 设置页"基础信息"等折叠面板无法渲染。

### 3.8 并行重复实现

#### 两套事件 reducer

```python
# A. story/state/apply_event.py — 接受 dict (legacy)
def apply_event(state, event: dict) -> StoryState

# B. story/events/reducer.py — 接受 StoryEvent dataclass (new)
def reduce(state, event: StoryEvent) -> StoryState
```

两者处理同一组事件类型（character_*/world_*/hook_*/commitment），但**事件模型不同**（dict vs dataclass），导致：

- StoryEngine 走 A 路径
- UnitRunner 间接通过 collect_signals 可能走 B
- 谁负责权威迁移？未明确

#### 两套 StateBridge

```python
# A. story/state/state_bridge.py  — DB → StoryState (运行时)
class StateBridge:
    def from_unit_v2(unit_v2) -> StoryState

# B. story/ui/bridge/state_bridge.py — StoryState → UI Event
class UIStateBridge:
    def on_state_change(old, new, diff)
```

这两个其实**职责不同**（一个翻译 DB→State，一个翻译 State→UI），命名却都叫 `state_bridge`，易混淆。

#### 两套 Agent 层次

```python
# A. app/agents/{writer,reader,critic,memory_agent,isolation}.py — 全部坏掉
# B. app/agents/helpers/{storyteller,editor,critic,retriever,memory_keeper,pressure_watcher,context_builder,researcher}.py — 实际工作
```

> 这是最容易让新人困惑的——同名文件 `critic.py` 出现在两个地方，行为完全不同。

## 四、方向：v4.1 "收口"

### 4.1 一句话方向

> **从"无限扩张架构"转向"垂直打透一个真实工作流"——以一个作者能完整跑完的"写一章 → 看因果 → 调指令 → 再生成"为北极星指标，把所有已写代码接入这条路径。**

### 4.2 三条核心原则（来自 v3.4 → v4.0 教训）

| 原则 | 反面教训 |
|---|---|
| **1. Integration First** | v4.0 写了 story/ 又留着 orchestrator 1131 行 → 两套并行 |
| **2. Delete > Refactor** | v4.0 给坏掉的 Agent 加了新 helpers/ 但没删旧的 → 误导新人 |
| **3. Human-in-the-Loop is the Product** | DeepSeek 说透了：作者要"数控机床"不要"香肠生产线" |

### 4.3 显式 NOT DO LIST（克制）

> 来自 v3.4 `v5 计划` 的智慧 + DeepSeek 评审的告诫：

```
❌ 不新增抽象层（不要再搞 story/decision/xxx_v3.py）
❌ 不做模块统一改名（命名一致性是 1 年后的事）
❌ 不实现 Graph 可视化（接受 checklist P3 部分延期）
❌ 不重写 prompt_assembler（已有，先接上再说）
❌ 不引入 pytest（先让 smoke 测试真起来）
❌ 不写新文档（除非是对当前真实代码的"准确镜像"）
❌ 不重命名 agents/ → helpers/ → story/（保留现状，但强制唯一入口）
```

### 4.4 整体战略：3 周路线图

```
Week 0: 基础设施清理（删除 + 接通）
Week 1: 接入 story/ 链路（一个真实工作流）
Week 2: 人工仲裁与可解释性（产品化）
Week 3: 文档与端到端验证（可演示）
```

| 阶段 | 目标 | 成功标准 |
|---|---|---|
| **W0** | 删除死代码 + 接通 story/ → orchestrator | `python -m app` 能用新路径生成一章 |
| **W1** | 跑通"写 → 因果 → 调指令 → 再生成"闭环 | 因果图真有数据、decision 真的记录 |
| **W2** | 实现"数控机床"：作者可暂停、可改、可回退 | 冲突消解日志 + 增量补丁可用 |
| **W3** | 一个真实 demo：写完 1 章、调整 3 处、再生成 1 章 | 录屏 + 验证报告 |

def _run_unit_v4(self, project_id, unit_id, **kwargs):
    # 1. 加载当前状态
    state = self._load_story_state(project_id, unit_id)
    
    # 2. 因果审查（P2）
    causal_review = self.review_causality(project_id, unit_id, state)
    if not causal_review.ok:
        # 写冲突日志，**不**阻止生成（Guidance 而非 Constraint）
        self._log_conflict(causal_review, project_id, unit_id)
    
    # 3. 调用 UnitRunner 全链路
    from story.runtime.unit_runner import UnitRunner
    runner = UnitRunner()
    result = runner.run(project_id, unit_id)
    
    # 4. 写后因果更新（P4）
    if result.ok and result.prompt:
        self.update_causal_graph(
            project_id, unit_id,
            draft_text=result.prompt.to_dict().get("messages", []),
        )
    
    return self._wrap_runresult(result)


def review_causality(self, project_id, unit_id, state) -> CausalReviewResult:

#### 5.10 增量补丁而非全量重编（P0）

**新文件**：`app/services/patch_preview.py`

```python
"""增量补丁预览 — Story Compiler 的正确实现方式。

不要直接改写源文件。
作者只改了一个配角的名字 → 不应该重生成 15 章。
应该是：
  1. StoryCompiler.analyze_impact() 找出影响范围
  2. 输出 patch_preview.md：高亮将被替换的句子
  3. 作者确认后，只替换指定句子
  4. 其他 99% 内容不动
"""
from dataclasses import dataclass, field
from difflib import SequenceMatcher


@dataclass
class PatchPreview:
    affected_unit_ids: list[str]
    changes: list["PatchChange"]
    estimated_api_cost: float        # 节省的费用
    estimated_time_seconds: float    # 节省的时间


@dataclass
class PatchChange:
    unit_id: str
    paragraph_index: int
    before: str
    after: str
    similarity: float  # 0-1，越低说明改动越大


def generate_patch_preview(
    project_id: str,
    change_description: str,         # "配角张三改名为李四"
    *,
    max_affected: int = 50,
) -> PatchPreview:
    """作者只描述改了啥，系统找出所有需要改的地方。"""
    # 1. 找到所有受影响的 unit
    affected = _find_affected_units(project_id, change_description)
    
    # 2. 对每个 unit 找出需要改的段落（不重生成）
    changes = []
    for unit_id in affected[:max_affected]:
        for idx, paragraph in enumerate(_get_paragraphs(unit_id)):
            new_text = _apply_local_replacement(paragraph, change_description)
            if new_text != paragraph:
                similarity = SequenceMatcher(None, paragraph, new_text).ratio()
                changes.append(PatchChange(
                    unit_id=unit_id,
                    paragraph_index=idx,
                    before=paragraph,
                    after=new_text,
                    similarity=similarity,
                ))
    
    # 3. 估算节省
    api_cost = len(changes) * 0.01   # 假设每段 1 分钱
    api_time = len(changes) * 2.0    # 假设每段 2 秒
    
    return PatchPreview(
        affected_unit_ids=affected,
        changes=changes,
        estimated_api_cost=api_cost,
        estimated_time_seconds=api_time,
    )


def apply_patches(preview: PatchPreview, confirmed_unit_ids: list[str]) -> int:
    """作者确认后，只对指定的 unit 应用补丁。其他不动。"""
    confirmed = set(confirmed_unit_ids)
    applied = 0
    for change in preview.changes:
        if change.unit_id not in confirmed:
            continue
        _replace_paragraph(change.unit_id, change.paragraph_index, change.after)
        applied += 1
    return applied
```

#### 5.11 反向编译（输出流程的核心创新）

**新文件**：`app/services/reverse_compile.py`

```python
"""反向编译：作者手动修改 → 反馈回 evidence_ids 权重。

闭环：AI 生成 → 人类润色 → 知识库固化
下次编译时，已经被作者认可的表达会优先出现。
"""
from pathlib import Path


def reverse_compile(project_id: str, chapter_id: str):
    """扫描作者对章节的修改，提取被认可的表达，更新到 evidence_ids 权重。"""
    # 1. 取 AI 生成的原始版本
    ai_version = _get_ai_generated_text(chapter_id)
    
    # 2. 取作者当前版本
    author_version = _get_current_text(chapter_id)
    
    # 3. diff
    diff = _diff_paragraphs(ai_version, author_version)
    
    # 4. 对每段被作者修改的：
    for change in diff:
        if change.significantly_modified:
            # 提升这段对应的 evidence_ids 权重
            for evidence_id in change.evidence_ids:
                _boost_evidence_weight(evidence_id, delta=0.1)
            
            # 如果作者删掉某句，可能是 AI 味
            if change.removed:
                _mark_as_anti_pattern(change.removed, source=chapter_id)
            
            # 如果作者新增，可能是好表达
            if change.added:
                _save_as_good_pattern(change.added, source=chapter_id)
```

## 九、给维护者的话

### 9.1 关于"完成"的标准

> 一个功能"完成"的定义不是"代码写好了"，而是"用户在产品里能用、能感知、有反馈"。
> 
> v4.0 的 Story Compiler 代码写好了，但用户在产品里点不到。
> 
> v4.1 的成功标准 = 用户能在产品里**实际触发** Story Compiler，**实际看到**影响范围，**实际决定**要不要改。

### 9.2 关于"测试通过"

> 一个测试"通过"的定义不是"assert 不报错"，而是"验证了一个**真实场景**下的**真实行为**"。
> 
> v4.0 的 35/35 测试通过了，但它们验证的是 mock 数据下的局部逻辑。
> 
> v4.1 的 smoke_v4_1_e2e.py 不接受 mock —— 它直接查询数据库，看真实写入。

### 9.3 关于"哲学"

> "Guidance 而非 Constraint" 不是一个 README 标语。
> 
> 它具体意味着：
> - 冲突发生时，**不**自动改文本，**而是写日志**告诉作者
> - 增量补丁时，**不**默认全量重编，**而是预览**让作者选
> - 反向编译时，**不**把作者修改覆盖掉，**而是吸收**到知识库
> 
> v4.1 的 conflict_log.py / patch_preview.py / reverse_compile.py 是这个哲学的**具体落地**。

### 9.4 关于"克制"

> v3.4 的 v5 计划给出了一份智慧的"禁止清单"：
> 不要重组目录、不要改名、不要删模块、不要做 Story Graph、不要统一命名。
> 
> v4.0 打破了一部分（重组 story/ 包、搞了两层 Agent）。
> 
> v4.1 必须**重新拥抱克制**：
> - 不新增抽象（只补 conflict_log / patch_preview / reverse_compile 这三个**用户能感知的**功能）
> - 不统一命名（接受 agents/ + helpers/ + story/ 三层共存）
> - 不做 Graph 可视化（v4.2 再说）

### 9.5 关于"方向"

> DeepSeek 说："你的项目是香肠生产线，作者要的是数控机床。"
> 
> 这个比喻的真正含义是：
> 
> - 香肠生产线 = 端到端全自动，无人工干预点
> - 数控机床 = 半自动，每个关键步骤都有"暂停 + 手动微调 + 继续"的接口
> 
> v4.1 不应该追求"全自动写完 100 万字"，
> 而是追求"作者能在每一章**任何位置**暂停，**任何理由**改，**任何粒度**恢复"。
> 
> 这是 product-market fit 的真正考验。
