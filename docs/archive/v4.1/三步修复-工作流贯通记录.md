# 三步修复：工作流贯通记录

> **实施日期**：2026-07-09 19:24-19:28  
> **定位**：不加新功能，只修断裂  
> **总改动量**：3 个文件，~130 行

---

## 背景

五份外部审计（GPT × 3 + Gemini × 2）的一致结论：

> **Story OS（Runtime）已经成熟，Product OS（工作流）尚未建立。**
> 26 个 Page 都有 `set_project` 方法（数据传播通道已存在），但**切页时不触发**——这就是"我改了大纲，写作页面不知道"的直接原因。

解决方案不是加新架构，而是在已有的通道上加一道"过门刷卡"的生命周期。

---

## Step 1：ProjectContext — 统一状态源

**文件**：`app/core/project_context.py`（新建，~80 行）

统一包裹 `current_project` 数据，提供 `save_to_disk()` 落盘入口。所有 Page 共享同一实例。

```python
class ProjectContext:
    def __init__(self):
        self.data = {"meta": {}, "settings": {}, "outline": {},
                     "characters": [], "current_content": ""}
    def load(self, path, data): ...
    def save_to_disk(self): ...
    def update_field(self, key, value): ...
```

---

## Step 2：生命周期钩子 — 切页刷卡

**文件**：`app/ui/main_window.py`（修改）

`_select_page` 方法增加两个生命周期钩子：

```python
def _select_page(self, page_id):
    # [离开] → 调 deactivate_and_save()    页面可选实现
    # [切换] → stack.setCurrentIndex(idx)
    # [进入] → 优先调 activate_and_refresh()
    #          降级调 set_project(project)   ← 覆盖全部 26 个页面
```

关键设计：
- `hasattr` 动态检查，未实现的页面保持原样（0 侵入性）
- `try/except` 包裹，防止单个页面的钩子崩溃卡死导航
- 降级路径确保即使不实现任何新方法，切页时也会自动重刷数据

**MainWindow 改动**：
- 创建 `self.context = ProjectContext()` 
- 所有 Page 实例化后注入 `page.context = self.context`
- `_set_current_project` 同步调用 `self.context.load()`

---

## Step 3：关键页面通电

**文件**：`app/ui/pages.py`（修改）

| 页面 | deactivate_and_save | activate_and_refresh |
|------|-------------------|-------------------|
| `generate`（写作） | 编辑器文本 → Context + 落盘 | 恢复正文 + 刷新项目数据 |
| `character-mgmt`（角色） | — | 进入时重刷角色列表 |
| `story-health`（观测） | — | 进入时重刷分析数据 |
| `publish`（发布） | 落盘 | 进入时重刷章节树 |

所有生命周期通过 `self.context` 操作统一状态源，不走独立数据路径。
