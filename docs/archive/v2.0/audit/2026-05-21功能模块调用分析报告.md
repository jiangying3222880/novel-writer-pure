## 三、问题模块详细分析

### 🔴 高风险 — 零生产调用

#### 1. BM25检索（app/rag/bm25.py）

- **现状**：`BM25Index`/`BM25Retriever` 在整个项目中零生产代码调用
- **与RAG的关系**：`RAGManager`（vector_db.py）和 `BM25Index`（bm25.py）完全独立，没有混合检索集成
- **建议**：
  - A：删除（RAGManager已覆盖向量检索需求）
  - B：集成到RAGManager实现混合检索（向量+关键词），提升检索质量

#### 2. 知识库打包（app/knowledge/bundle.py）

- **现状**：`ensure_knowledge_bundle`/`KnowledgeBundle` 零生产调用
- **与知识库检索的关系**：`finder.py` 直接读取 `bundle.enc`，但 `bundle.enc` 的生成/更新没有业务流程触发
- **建议**：
  - A：删除（finder.py已覆盖检索需求，bundle.enc是预生成的）
  - B：接入CLI命令，提供 `knowledge bundle` 命令手动打包

#### 3. 文档解析器（app/tts/document_parser.py）

- **现状**：仅测试文件引用，`TTSManager` 未调用 `parse_markdown`
- **调用链断裂**：`document_parser.parse_markdown()` → 应被 `TTSManager` 调用 → 实际未调用
- **建议**：
  - A：删除（TTSManager只用sentence_splitter，不需要Markdown解析）
  - B：接入TTSManager，朗读Markdown/PDF文档时先解析再分割

#### 4. DAO层 — ChapterDAO / CharacterDAO / ProjectDAO

- **现状**：3个DAO类零生产调用，UI和Agent全部直接用 `project_db` 函数式API
- **仅HookDAO和WorldDAO**被dashboard_tab和entity_graph少量使用
- **架构问题**：DAO层与project_db形成两套并行数据访问路径，功能完全重复
- **建议**：
  - A：删除全部DAO层，统一使用project_db（简单直接）
  - B：删除ChapterDAO/CharacterDAO/ProjectDAO，保留HookDAO/WorldDAO，逐步迁移UI到DAO层
  - C：全面迁移到DAO层，废弃project_db的函数式API（工程量大）

---

### ⚠️ 中风险 — 调用链断裂或功能重复

#### 5. CLI命令（app/cli/commands.py）

- **现状**：定义了完整的Click命令组（project/chapter/workflow/knowledge/model/db/version/license/log），但：
  - 无任何Python模块import它
  - `pyproject.toml` 中没有 `[project.scripts]` 入口点定义
  - `main.py` 中仅通过 `--cli` 参数做简单打印，未调用Click命令
- **建议**：
  - A：删除（GUI应用不需要CLI）
  - B：在pyproject.toml中注册入口点，让CLI可用

#### 6. 模型查找器（providers.py中lookup函数）

- **现状**：`lookup_model`/`find_provider_for_model`/`get_forced_temperature` 外部零import
- **功能重复**：`step_model_config.py` 自行实现了 `_resolve_model_name`，没有复用lookup函数
- **建议**：让 `step_model_config.py` 复用 `lookup_model`，删除重复逻辑

#### 7. 安全模块（app/core/security.py）

- **现状**：仅被 `license.py` 内部使用，暴露了公共API（`SecurityManager`/`get_security_manager`）却无外部调用
- **建议**：合并到 `license.py`，不单独暴露

#### 8. db/orm/ 目录

- **现状**：仅做re-export（从 `app.db.models` 导入再导出），被 `app/db/__init__.py` 使用
- **建议**：删除 `orm/` 目录，让 `app/db/__init__.py` 直接从 `app.db.models` 导入

## 四、架构层面问题

### 问题1：UI直接用project_db，绕过DAO层

```
当前架构：
  UI/Agent → project_db（函数式API，50+函数）→ SQLite
  DAO层    → project_db（类方法API，5个类）   → SQLite  ← 几乎无人用

问题：
  - 两套并行数据访问路径，功能重复
  - DAO层有类型安全优势，但无人用
  - project_db 函数式API更直接，但缺少类型约束
```

### 问题2：RAG系统内部未集成BM25

```
当前架构：
  RAGManager（vector_db.py）→ 向量检索 → 独立运行
  BM25Index（bm25.py）      → 关键词检索 → 完全孤立

理想架构：
  RAGManager → 混合检索（向量 + BM25）→ 更高质量的检索结果
```

### 问题3：知识库打包/解包未接入业务流程

```
当前架构：
  bundle.py → 打包/解包功能 → 零调用
  finder.py → 直接读bundle.enc → 正常工作

问题：
  - bundle.enc 是预生成的，没有更新机制
  - knowledge/ 目录有200+素材文件，但没有流程触发重新打包
```

## 七、各模块在工作流中的位置详解

### 核心流程模块

| 模块 | 在哪一步使用 | 输入 | 输出 | 输出传给谁 |
|------|------------|------|------|-----------|
| **工作流引擎** | 贯穿全程 | 项目ID、章节号 | 协调8步流程 | UI主窗口 |
| **AI引擎** | 每一步都调用 | 提示词+参数 | AI生成的文本 | 当前步骤的Agent |
| **风格清理器** | 每一步都调用 | AI原始输出 | 清理后的文本 | 当前步骤的Agent |
| **核心CRUD** | 准备阶段+收尾阶段 | SQL查询 | 数据库数据 | 所有模块 |

### 合同与故事体系

| 模块 | 在哪一步使用 | 输入 | 输出 | 输出传给谁 |
|------|------------|------|------|-----------|
| **故事体系** | 准备阶段（生成合同）+ 收尾阶段（提交合同） | 章节号、前章状态 | 写作合同（必须完成的事件/伏笔） | 规划师 |
| **合同数据结构** | 准备阶段+收尾阶段 | 章节事件、字数、追读力评分 | 结构化合同数据 | 故事体系 |
| **事件审计链** | 准备阶段+每步完成+收尾阶段 | 事件类型+数据 | 审计日志 | 日志系统 |

### 第1步：规划师

| 模块 | 用途 | 输入 | 输出 |
|------|------|------|------|
| **题材模板加载** | 加载题材相关的写作规范 | 题材名称 | 题材规范文本 |
| **步骤模型配置** | 获取规划师步骤使用的AI模型 | 步骤名"planner" | 模型名称 |

### 第2步：写手

| 模块 | 用途 | 输入 | 输出 |
|------|------|------|------|
| **节奏追踪器** | 获取三线节奏约束 | 章节号 | 主线/副线/暗线约束文本 |
| **AI痕迹检测** | 检测初稿中的AI味 | 章节文本 | AI痕迹列表+去味建议 |
| **后写验证器** | 验证初稿基本质量 | 章节文本 | 验证结果（通过/不通过） |
| **跨章检查器** | 检查与前章一致性 | 当前章+前章文本 | 一致性报告 |

### 第3-4步：深度读者/深度编辑

| 模块 | 用途 | 输入 | 输出 |
|------|------|------|------|
| （仅AI引擎+风格清理器） | 阅读反馈/深度编辑 | 章节文本 | 反馈报告/编辑后稿件 |

### 第5步：审核员

| 模块 | 用途 | 输入 | 输出 |
|------|------|------|------|
| （仅AI引擎+风格清理器） | 审核是否满足约束 | 章节文本+约束清单 | 通过/不通过+问题列表 |

### 第6步：修订员

| 模块 | 用途 | 输入 | 输出 |
|------|------|------|------|
| **AI痕迹检测** | 检测修订稿中的AI味 | 修订后文本 | AI痕迹列表+去味建议 |
| **后写验证器** | 验证修订稿基本质量 | 修订后文本 | 验证结果 |
| **跨章检查器** | 检查与前章一致性 | 当前章+前章文本 | 一致性报告 |

### 第7步：结算员

| 模块 | 用途 | 输入 | 输出 |
|------|------|------|------|
| **追读力分析** | 计算追读力评分 | 章节文本 | 追读力评分（0-10分） |
| **内容分析器** | 分析角色事件和感情线 | 章节文本 | 角色事件列表+感情线变化 |

### 收尾阶段

| 模块 | 用途 | 输入 | 输出 |
|------|------|------|------|
| **记忆管理器** | 更新短期/长期记忆 | 章节摘要+角色状态 | 更新后的记忆库 |
| **故事体系** | 提交合同，更新故事状态 | 合同+最终稿件+追读力评分 | 故事状态更新 |
