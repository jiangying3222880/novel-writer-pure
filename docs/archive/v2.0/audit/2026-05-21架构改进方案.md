## 集群A：合同与规则引擎体系（原问题1+5）

### 合并理由

问题1（全书合同）和问题5（合同验收）是同一体系的两面——合同定义了约束，验收执行了约束。分开实施会导致合同生成了但没人校验（当前状态），或校验了但没有合同可校验。

### 现状分析

当前合同系统是**空壳**——零约束力：

| 缺陷 | 说明 |
|------|------|
| 合同从未被保存 | `generate_contract` 返回对象后，从未调用 `save_contract()` |
| 合同从未传递给任何Agent | `contract` 变量仅存在于Engine局部作用域 |
| 合同字段全部为空 | prohibitions/core_conflict/hooks_plant/hooks_reap/debt_tracking 全为默认空值 |
| `preflight_check` 从未被调用 | 5项检查逻辑已实现但永远不执行 |
| `commit` 不回写任何状态 | 仅保存极简StoryEvent JSON，缺少9个关键字段 |
| `MasterSetting` 本身也是空壳 | 从不存在的JSON加载，返回硬编码默认值 |

当前Planner.verify()的验收只有4条标准，且全部是AI软判断，没有硬约束校验。

### ✅ 已决策方案：BookContract + RuleEngine + AIConsultant（问题1方案C）

渐进式实现路线：

| 阶段 | 内容 | 确定性 | AI调用 |
|------|------|--------|--------|
| 阶段1 | BookContract数据结构 + 激活已有preflight_check | 100% | 无 |
| 阶段2 | RuleEngine规则引擎（硬约束校验、伏笔追踪、完成状态管理） | 100% | 无 |
| 阶段3 | AIConsultant可选AI咨询（跨章分析、动态调整建议） | 不确定 | 可选 |

### 合并问题5：双层验收

合同验收分为两层，与方案C的RuleEngine对齐：

| 层 | 执行者 | 校验内容 | 性质 | AI调用 |
|----|--------|---------|------|--------|
| **确定性层** | RuleEngine | 禁止项违反、伏笔计划执行、字数达标、三线比例偏离 | 硬约束 | 无 |
| **AI层** | Planner.verify() | 约束清单覆盖、伏笔回收质量、角色一致性、剧情走向、合同精神 | 软约束 | 1次 |

验收流程：

```
章节写作完成
  → RuleEngine.post_write_check()（确定性校验）
    ├─ 不通过 → Reviser修订 → 再检查（最多2轮）
    └─ 通过 → Planner.verify()（AI验收，5条标准）
      ├─ 不通过 → Reviser修订 → 再验收（最多2轮）
      └─ 通过 → 进入Polisher/Settler
```

Planner.verify() 验收标准从4条增加到5条：

| 序号 | 验收标准 | 性质 |
|------|----------|------|
| 1 | 章节是否覆盖了约束清单中的所有必选要素 | AI判断 |
| 2 | 伏笔回收是否到位 | AI判断 |
| 3 | 角色行为是否与设定一致 | AI判断 |
| 4 | 剧情走向是否符合规划 | AI判断 |
| 5 | 是否符合合同精神（核心冲突是否展开、追读力是否达标趋势） | AI判断 |

## 集群B：Agent架构与记忆体系（原问题2+3+4+12）

### 合并理由

问题2（Agent+记忆）、3（合并Agent）、4（Polisher启用）、12（蒸馏联动）是同一体系——Agent数量和记忆架构决定了蒸馏触发策略，合并Agent后记忆配置也要调整，Polisher从可选变固定也影响Agent编号。

### 现状分析

**Agent问题**：当前8个Agent，DeepReader+DeepEditor+Auditor重叠度60%，Polisher可选但应默认启用。

**记忆问题**：STM偏离设计初衷（20条事件 vs 前3章摘要），Agent无法直接访问STM，私有记忆不持久化。

**蒸馏问题**：只在STM溢出时被动触发，STM重构后触发条件需重写。

### 方案：7个Agent + STM重构 + 蒸馏联动

#### 1. Agent精简（问题3+4）

合并DeepReader+DeepEditor到Auditor，Polisher默认启用：

```
当前8步：Planner → Writer → DeepReader → DeepEditor → Auditor ↔ Reviser → Polisher(可选) → Verify → Settler
优化7步：Planner → Writer → Auditor(增强版) ↔ Reviser → Polisher(默认启用) → Verify → Settler
```

增强版Auditor整合三视角：

```
增强版Auditor（三视角合一）
├── 读者视角检查（原DeepReader差异化项：吸引力/爽点/悬念/情感共鸣）
├── 编辑视角检查（原DeepEditor差异化项：结构/开头/结尾/对话/描写/视角/逻辑/冲突）
└── 六维量化评分（原Auditor核心：D01爽点密度/D02一致性/D03节奏/D04 OOC/D05连贯性/D06追读力）
```

优势：3次AI调用→1次，节约约60% tokens。评分直接基于检查结果，不再独立重新审查。

#### 2. STM重构（问题2核心）

**设计初衷**：聚焦当前章节 + 前3章摘要

**重构方案**：滑动窗口 + 分层摘要 + Agent按需读取

```
STM窗口（滑动窗口，每章写作时重建）：
├── 当前章节上下文（章节号/标题/大纲要点/涉及角色/需回收伏笔）
├── 前1章摘要（完整摘要，约200字）
├── 前2章摘要（精简摘要，约100字）
├── 前3章摘要（极简摘要，约50字）
└── 更早章节 → 已蒸馏到LTM，不保留在STM中
```

Agent新增接口：

```python
def recall_stm(self, chapter_no: int) -> str:
    """读取聚焦当前章节的STM上下文（滑动窗口摘要）"""

def build_context_for_step(self, step_name: str, chapter_no: int) -> str:
    """按步骤需求定制记忆上下文"""
```

按步骤定制的记忆上下文：

| 步骤 | 需要的记忆 | 不需要的 |
|------|-----------|---------|
| Planner | LTM核心设定 + STM前3章摘要 + 活跃伏笔 + 全书合同 | 角色状态细节、物品追踪 |
| Writer | LTM角色设定 + STM前1章完整摘要 + 角色状态 + 本章伏笔 | 世界规则细节、蒸馏摘要 |
| Auditor | STM前3章摘要 + 角色状态 + 活跃伏笔 | 世界规则、物品追踪 |
| Reviser | STM前1章摘要 + 角色状态 + 审核问题 | 世界规则、蒸馏摘要 |
| Polisher | STM前1章摘要 | 伏笔、物品追踪 |
| Settler | 全部记忆（用于结算和蒸馏） | 无 |

STM容量调整：

| 参数 | 当前 | 重构后 |
|------|------|--------|
| `stm_max_size` | 20条事件 | 3章摘要 + 当前章节上下文 |
| 加载范围 | `current_chapter_no - 5` 到 `+1` | `current_chapter_no - 3` 到 `current_chapter_no` |
| 淘汰策略 | 按重要性淘汰 | 滑动窗口（超出3章自动淘汰） |
| 摘要精度 | 统一格式 | 递减精度（前1章200字→前3章50字） |

#### 3. 蒸馏联动（问题12）

STM重构后，蒸馏触发策略重写：

| 策略 | 当前 | 修订后 |
|------|------|--------|
| 触发条件 | STM溢出（>20条事件） | STM滑动窗口淘汰时 **或** 每N章强制蒸馏 |
| 蒸馏时机 | 被动触发 | Settler中主动触发 + STM淘汰时自动触发 |
| 蒸馏输入 | STM事件 + LTM蒸馏摘要 + 角色状态 | 淘汰的章节摘要 + LTM蒸馏摘要 + 角色状态 |

蒸馏流程：

```
第N章写作完成
  → Settler结算，生成章节摘要
  → STM更新：加入第N章摘要，淘汰第N-4章摘要
  → 淘汰的摘要自动触发蒸馏 → 压缩到LTM的distilled_summary
  → RuleEngine里程碑检查（每10章强制蒸馏）
  → 下次写作时，STM只有前3章，更早的通过LTM蒸馏摘要获取
```

#### 4. Agent记忆持久化

- 私有记忆 → 保存到数据库 `agent_memory` 表（agent_name + key + value）
- 共享记忆写权限 → 放宽到所有Agent都可写，但限定key前缀
- 每次运行开始时从数据库加载私有记忆

7个Agent的记忆配置：

| 步骤 | Agent | 记忆配置 |
|------|-------|----------|
| 1 | PlannerAgent | 读LTM + 读STM + 写私有记忆 |
| 2 | WriterAgent | 读LTM + 读STM + 写私有记忆 |
| 3 | AuditorAgent（增强版） | 读LTM + 读STM + 写私有记忆 |
| 4 | ReviserAgent | 读LTM + 读STM + 写私有记忆 |
| 5 | PolisherAgent | 读LTM + 读STM + 写私有记忆 |
| 6 | PlannerAgent.verify | 读LTM + 读STM + 读全书合同 |
| 7 | SettlerAgent | 读写LTM + 写共享记忆 + 主动触发蒸馏 |

问题7（知识库加载）、9（混合检索）、10（知识库检索加入Agent）、14（BM25零调用）是同一体系——知识库的目录结构决定了检索方式，检索方式决定了Agent如何获取知识，BM25是检索的组成部分。分开实施会导致加载了知识库但检索不到、或检索了但Agent不用。

#### 方案B+C：统一步骤缓存（DB查询 + STM + 知识库 + 混合RAG检索）

综合集群A/B/C的决策，缓存包含4层：

```python
# engine.py
def _preload_all_cache(self, chapter_no: int, genre: str):
    # 1. DB缓存
    self._get_cached(f"prev_summary_{chapter_no}", lambda: db.get_previous_chapter_summary(...))
    self._get_cached(f"char_list_{chapter_no}", lambda: db.get_character_list_str(...))
    self._get_cached(f"meta_{chapter_no}", lambda: db.get_meta(...))
    self._get_cached(f"chapter_content_{chapter_no}", lambda: db.get_chapter_content(...))

    # 2. STM缓存（集群B）
    self._get_cached(f"stm_{chapter_no}", lambda: self.mm.get_stm_focused(chapter_no))

    # 3. 知识库缓存（集群C：按步骤分类+题材过滤）
    for step, categories in STEP_KNOWLEDGE_MAP.items():
        for category in categories:
            self._get_cached(
                f"knowledge_{step}_{category}_{genre}",
                lambda c=category: self._knowledge(step, chapter_no, categories=[c], genre=genre)
            )

    # 4. RAG缓存（集群C：混合检索+category+genre过滤）
    for category in ["character", "hook", "chapter"]:
        self._get_cached(
            f"rag_{category}_{chapter_no}_{genre}",
            lambda c=category: self._rag_retrieve(
                query=f"第{chapter_no}章", categories=[c], genre=genre, top_k=5
            )
        )
```

**预计节省**：
- 方案A：减少约150行重复代码
- 方案B+C：每章减少约10次DB查询 + 约15次RAG检索
- 合计：每章节约约25次重复调用

## 集群E：实体图谱集成（原问题11）

### 合并理由

实体图谱独立成集群，因为它横跨A（RuleEngine校验角色关系）、B（STM集成角色关系数据）、C（从03_人物人设库增强数据）三个集群，但自身改动量不大。

### 方案：预加载+缓存+STM集成+RuleEngine联动

1. **Engine层预加载EntityGraph** → 缓存（集群D）
2. **BaseAgent注入EntityGraph**
3. **PlannerAgent** — 查询本章涉及角色的关系网络 → 写入STM当前章节上下文
4. **WriterAgent** — 查询角色间关系，确保对话和互动符合关系设定
5. **RuleEngine**（集群A）— 合同校验时检查角色关系约束
6. **知识库联动**（集群C）— 从03_人物人设库增强角色关系数据

### 影响文件

- `app/workflow/agents/base.py` — 注入entity_graph

- `app/workflow/agents/planner.py` — 查询角色关系 + 写入STM
- `app/workflow/agents/writer.py` — 查询角色关系
- `app/workflow/rule_engine.py` — 合同校验时检查角色关系约束
- `app/memory/entity_graph.py` — 增加从知识库增强数据的能力
