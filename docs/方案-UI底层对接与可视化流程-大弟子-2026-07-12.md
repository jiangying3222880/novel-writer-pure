## 一、现状：三层架构调用链全景

```
用户操作 (UI)
    │
    ▼
NAV_TREE 5 分组 → 25 个 PAGE_ID
    │
    ├── 项目管理: ProjectsPage → project_service + project_io
    ├── 故事设定: 5 个 TAB → book/chapter/outline/worldbuilding/character
    ├── ✍ 开始写作: GenerateTab → Orchestrator → StoryEngine (10步)
    │   ├── 写作向导 → WritingWizard
    │   ├── 当前创作 → GenerateWorker/OrchWorker
    │   ├── 故事单元 → _OrchUnitWorker + StoryUnitTab
    │   └── 单元池 → UnitPoolTab
    ├── 📊 仪表盘: DashboardTab → dashboard_service + pressure
    └── ⚙ 设置: knowledge/model/appearance/storage/about

        底层引擎 (10步管线)
            │
            ▼
❶ 加载状态 → ❷ Guide收集(4子步骤) → ❸ Agent研究(5个并行) → ❹ 精炼提示
→ ❺ 因果审查 → ❻ 写作 → ❼ 评估(改稿循环) → ❽ 落库 → ❾ 后处理 → ❿ 通知UI

        UI 回调通道
            │
            ├── on_step(step, label)  ← 仅序号+标签，无元数据
            ├── UIStateBridge         ← 仅在管线完成后触发一次
            └── OrchestratorResult    ← 仅在调用线程阻塞完成后可读
```

## 二、核心问题：4 类"黑箱"模式

### 类型 A：信号定义了但从未发射（5 处）

这是最典型的问题模式——Worker 定义了 progress/thinking/chunk 信号，但 run() 中从未 emit。

| # | 位置 | 定义 | 实际 emit? |
|---|------|------|:---:|
| A1 | `generate_tab.py:194` | `_OrchUnitWorker.progress = Signal(int, bool)` | ❌ 定义但从未 emit → 进度条始终 0% |
| A2 | `generate_tab.py:87` | `GenerateWorker.thinking = Signal(str)` | ❌ 从不 emit → `_on_thinking()` 永不被调 |
| A3 | `generate_tab.py:148` | `OrchWorker.thinking = Signal(str)` | ❌ 同上 |
| A4 | `generate_tab.py:85` | `GenerateWorker.step = Signal(int, str, dict)` | ⚠️ emit 了但第三个参数永远是 `{}` |
| A5 | `generate_tab.py:178` | `OrchWorker.step` 同上 | ⚠️ 同上 |

**根因**：Worker 层只管转发，但 Orchestrator/StoryEngine 的 `on_step` 回调和 `_dispatch()` 没有传递元数据的能力。

### 类型 B：子步骤不可见（3 处）

一个大步骤内部包含多个真实的 AI 调用，但 UI 只看到一个标签。

| # | 大步骤 | 实际子步骤 | 用户看到 | 影响 |
|---|--------|-----------|---------|------|
| B1 | Step 1 "Guide 收集" | signals→decide→suc→compile 4 个子步骤 | 一个标签停留很久 | 不知道"卡"在哪 |
| B2 | Step 2 "Agent 研究" | Memory→Context→Research→Pressure→Retrieve 5 个 Agent | 一个 "Agent 研究" 标签 | 不知正在执行哪个 Agent |
| B3 | Step 6 "评估" | Editor→Critic→改稿循环(多轮) | 一个 "评估" 标签 | 不知改到第几轮、分数多少 |

**根因**：StoryEngine 和 Orchestrator 的步进步进粒度为 10 步，但实际 AI 调用粒度是 15-20 个操作。

### 类型 C：结果只事后可见，不实时推送（4 处）

| # | 数据/结果 | 当前可见时机 | 应该是 |
|---|---------|------------|--------|
| C1 | 叙事压力值 | 仅在 Dashboard 手动查看 | 写作中 StoryHUD 实时显示 |
| C2 | Agent 研究报告 | 仅在 OrchestratorResult 中返回 | 写作中可折叠查看 |
| C3 | 改稿分数/轮次 | 仅在评估循环结束后 | 每一轮改稿的分数变化 |
| C4 | StoryHUD 状态 | 仅在 `STORY_STATE_UPDATED` 事件后（管线完成） | 写作中随步骤更新 |

**根因**：`UIStateBridge._notify_ui()` 仅在管线全部完成后触发一次（story_engine.py:459），没有中间状态推送。

### 类型 D：事件总线空转（73% 事件无订阅）

22 个事件中仅 6 个有 UI 层订阅者：

```
有订阅 (6):
  STORY_STATE_UPDATED   → StoryHUD
  STORY_UNIT_COMPLETED  → DashboardTab
  ROUTER_USED/FAILED/CACHE_HIT/FALLBACK → RouterStatusBar

无订阅 (16):
  CHAPTER_GENERATING/GENERATED/SAVED/EVALUATED/FINISHED/COMMITTED
  EDIT_SIGNAL_INGESTED
  CANDIDATE_PROMOTED/EVOLVED
  SKILL_INJECTED
  SUBTEXT_GENERATED
  WORLD_SYNCED
  CONTRADICTION_FOUND
  PROJECT_SWITCHED
  APP_STARTED/CLOSING
  STORY_UNIT_COMPLETED
```

**根因**：事件定义是为了「以后用」，但没有对应的 publish() 调用和 UI subscribe()。

有几处 UI 代码已经写好了接收元数据/中间结果的逻辑，但后端从未提供数据：

## 四、可落地方案（三阶段）

### 第一阶段：接线（1-2 天）— 激活已有 UI 能力

这些都是「后端改 emit，UI 已经就绪」的最低成本改造。

| # | 改造 | 改动位置 | 行数 |
|---|------|---------|:---:|
| P1 | `_OrchUnitWorker` emit progress 信号 | `generate_tab.py:193-225` 在 `run()` 中 `self.progress.emit(current, total)` | ~5 行 |
| P2 | GeneratorWorker/OrchWorker emit thinking 信号 | 从 Orchestrator `_dispatch()` 获取 agent.execute() 的中间输出 | ~10 行 |
| P3 | step 信号填充元数据 dict | `story_engine.py:107-112` 的 `on_step(step, label)` → `on_step(step, label, meta)` | ~15 行 |
| P4 | 评估改稿循环每轮 emit score 变化 | `orchestrator.py:448-494` 中 emit step 信号 + score 数据 | ~8 行 |
| P5 | StoryHUD 在写作中途订阅事件 | 新增 `STORY_STATE_UPDATED` 在管线中途发布（非仅完成时） | ~10 行 |

**效果**：用户立刻能看到 → 进度条正常、Agent 思考可见、各步元数据（tokens/字数/压力）在 WritingFlowDialog 展示

### 第二阶段：子步骤可视化（2-3 天）— 细化管线展示

## 五、优先级矩阵

```
               改动量小
                 │
    P1 P2 P3    │   P6 P7 P8
    (接线)      │   (子步骤)
                 │
  ───────────────┼──────────────────
                 │
    P4 P5       │   P9 P10 P11 P12
    (元数据)    │   (事件驱动)
                 │
                 │ 改动量大
```

| 象限 | 含义 | 建议 |
|------|------|------|
| 左上 | 低改动 × 高价值 | **第一批，立即做** |
| 右上 | 中改动 × 高价值 | 第二批 |
| 右下 | 高改动 × 高价值 | 第三批 |
| 左下 | 低改动 × 低价值 | 穿插做 |

## 六、一个关键架构决策

当前 `on_step(step, label)` 回调只传两个参数。如果改为 `on_step(step, label, meta: dict)`：
- **向上兼容**：现有 `_on_step()` 方法只需加一个可选参数
- **对下游成本**：`GenerateWorker`, `OrchWorker`, `_OrchUnitWorker` 的 step.emit 调 3 处
- **收益**：WritingFlowDialog 的 `_on_step_with_meta`、`EvaluationPanel`、`StoryHUD` 三个已写好的 UI 组件立即生效

这个改动是打通元数据通道的**唯一瓶颈**。建议作为 P0 前置条件在第一天完成。
